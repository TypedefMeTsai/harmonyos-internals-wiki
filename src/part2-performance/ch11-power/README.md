# 第 11 章：功耗

功耗问题和前面几章的性能问题有一个本质区别：卡顿和时延是用户当场感知的，功耗是用户事后感知的——"今天没怎么用手机，电怎么没了"。没人能指出是哪个瞬间掉的电，但投诉会算在整个系统头上，系统再把账算到应用头上。华为应用市场对后台任务、后台硬件资源、后台 CPU 负载都有明确的上架规则约束（出处：《后台任务合理使用》《后台硬件资源合理使用》），功耗不合规是实打实的上架风险，不只是体验问题。

鸿蒙的功耗治理思路是"系统统一管控 + 应用按需申请"。应用退到后台后，系统默认会挂起甚至终止进程，挂起后 CPU、网络、GPS、蓝牙、定时器、公共事件全部不可用；确实需要后台运行的业务，必须通过 Background Tasks Kit 申请规范内受约束的后台任务——短时任务、长时任务、延迟任务、代理提醒——每种都有明确的适用场景、配额和监管。这套机制决定了：功耗优化的第一课不是"怎么省电"，而是"怎么在规则内正确地活着"。

本章两节：

**11.1 功耗模型与后台资源管控。** 建立功耗的基本分析框架：电耗在哪些硬件模块上（显示、CPU/GPU、网络、音频、传感器），应用行为如何映射到这些模块的耗电；讲清楚后台资源管控的两个手段（进程挂起与进程终止）、挂起后失去什么、以及官方对后台 CPU 负载的量化约束（后台进程持续 10 分钟 CPU 使用率不得高于 80%）。

**11.2 长时任务与唤醒治理。** 四种后台任务各自怎么用、配额怎么算；然后把视角切到一个隐蔽但高发的功耗源头：冗余的 Vsync 请求。页面静止时，一个忘记注销的 displaySync 对象能让 UI 以 60Hz 持续空刷——应用主线程每帧空跑、RS 每帧空转。官方《Vsync 低功耗优化》给出的案例里，解注册 displaySync 对象后 UI 帧率直接降到 0Hz。这一节会讲清楚 Vsync 的"发车模型"、三类关键 Trace 点，以及 displaySync / NativeVsync / 第三方框架帧回调的治理方法。

功耗分析的工具（Energy 模板、SmartPerf 的功耗采集、电量统计）在第 13、14 章展开，本章专注机制与规则。读完应该能回答：我的应用凭什么在后台运行、静止时它为什么还在耗电、电到底花在哪。
