# 7.1 丢帧故障模型：AppDeadlineMissed 与 RenderDeadlineMissed

## 为什么要先建立故障模型

用 DevEco Profiler 的 Frame 模板录一段滑动场景的 Trace，我们会看到两条平行的帧泳道：一条标着 App Frame，一条标着 RS Frame。绝大多数帧是绿色的，偶尔出现一两个红色块。鼠标悬停上去，冒泡信息里写着 Jank Type：AppDeadlineMissed 或 RenderDeadlineMissed。

这两个名字就是鸿蒙丢帧分析的入口。它们不是笼统的"卡顿"，而是系统对每一次丢帧的责任判定：应用侧没有在一个 Vsync 周期内交出渲染数据，记 AppDeadlineMissed；Render Service 侧拿到了数据但没有按时画完，记 RenderDeadlineMissed。判定结果直接写在 Trace 里，我们要做的是读懂它，然后沿着对应一侧的泳道往下查。不先分清这两类故障，分析就会变成在几十条泳道里无目的地翻找。

## 统一渲染管线与 Vsync 周期

第 2 章已经讲过统一渲染的机制，这里从丢帧角度再回顾一遍流水线结构。

HarmonyOS 图形系统采用统一渲染模式，遵循流水线模式（出处：《帧率问题分析》）。整个流程分三段：

1. **应用侧**：响应输入事件、处理动画和状态变更，生成界面描述数据结构——包括 UI 元素的位置、大小、资源、绘制指令和动效属性。应用在 Vsync 信号驱动下完成 Animation、Events、UpdateUI、Measure、Layout、Render、SendMessage 这一串阶段，然后通过 IPC 把绘制指令提交给 Render Service。
2. **Render Service（RS）**：图形栈中负责界面内容绘制的系统进程。RS 的 RenderThread 线程在 Vsync 信号触发下进行 UI 绘制，绘制过程包含动效、描画和提交三个阶段，协调 GPU 资源完成合成。
3. **Display**：显示屏幕的抽象，包括物理屏和虚拟屏，最终把合成结果送到硬件上屏。

[图：90Hz 刷新率下的渲染流水线。横向时间轴上标出连续的 Vsync 周期，应用侧在第 N 个周期内完成 UI 处理并提交，RS 侧在第 N+1 个周期内完成绘制合成，屏幕在第 N+1 个周期末刷新出画面。三段首尾相接，任何一段超期都会推迟最终上屏时间。]

驱动这条流水线的节拍器是 Vsync。不同刷新率下，一个 Vsync 周期的时长为（出处：《帧率问题分析》）：

| 刷新率 | Vsync 周期 |
| --- | --- |
| 60Hz | 16.7ms |
| 90Hz | 11.1ms |
| 120Hz | 8.3ms |

120Hz 设备上，应用侧和 RS 侧各自能花的时间都以 8.3ms 为预算。这个预算是理解后面所有"期望时间"概念的基准：Frame 泳道上每一帧都有一个期望开始时间（Expected Start）和期望结束时间（Expected End），由当前刷新率算出；帧的实际结束时间晚于期望结束时间，就被判定为卡顿（出处：《Frame 分析》）。官方文档中的真实案例：一台 120Hz 设备上，某帧期望处理时间 8.3ms，实际处理 8.9ms，只超了 0.6ms，依然被标红记为丢帧。

## 两类丢帧故障模型

应用侧和 RS 侧都可能卡顿，最终用户都观测到丢帧。系统把这两种情况分别命名为 AppDeadlineMissed 和 RenderDeadlineMissed（出处：《帧率问题分析》）。

**AppDeadlineMissed（应用侧卡顿）**：应用没有在自己的时间预算内完成 UI 处理并提交渲染指令。通常由应用逻辑代码处理效率低引起：主线程上跑了耗时计算、同步 I/O；组件树太大、标脏范围太广，Measure/Layout 做不完；长列表滑动中频繁创建新组件等。第 9 章会讲的主线程阻塞是它的极端形态。

**RenderDeadlineMissed（RS 侧卡顿）**：应用按时提交了，但 RS 没有画完。可能由界面结构复杂（图层数量多、叠加混合多）、GPU 渲染负载高（大纹理、复杂滤镜、离屏渲染）导致。应用开发者对这一类也不是完全无能为力——图层数量、图片尺寸、模糊和阴影效果都是应用侧决定的。

[图 1：AppDeadlineMissed 故障模型。App Frame 泳道上一帧的实际耗时跨过期望结束线，红色延伸到下一个 Vsync 周期；对应的 RS Frame 因为等不到应用数据，同样错过自己的截止时间，最终屏幕重复显示上一帧。]

[图 2：RenderDeadlineMissed 故障模型。App Frame 按时完成（绿色），RS Frame 超时（红色），最终同样丢帧。两图对比说明：用户看到的丢帧现象相同，但 Trace 上红在哪条泳道，决定了排查方向。]

在 Frame 模板中可以直观看到这两个故障模型。判读规则如下（出处：《帧率问题分析》《Frame 分析》）：

- 在带 RS Frame 和 App Frame 标签的子泳道中，正常完成渲染的帧显示为**绿色**，出现卡顿的帧显示为**红色**。
- 红色帧内部再细分：**期望结束时间点之前的部分为浅红色**（两条白色竖线区间），**超出期望结束时间的部分为深红色**。浅红告诉我们这帧已经知道自己要超期，深红的长度就是超期的量。
- **异常帧显示为黄色**。
- 如果帧超时，泳道上会显示两条竖线，对应期望开始时间和期望结束时间，用于关联分析同一时刻的 Trace 或函数采样信息。
- 卡顿丢帧类型（Jank Type）有三种取值：No Jank（不卡顿）、AppDeadlineMissed（App 侧卡顿）、RenderDeadlineMissed（Render Service 侧卡顿）。

一个容易误解的点：App 侧帧和 RS 侧帧不是一一对应的。一帧的绘制一般由 App 侧提交到 RS 侧，RS 侧再提交给硬件合成，可能多个 App 侧帧提交到同一个 RS 侧帧上，出现一对多的关联（出处：《Frame 分析》）。看 Trace 时不要假设两边帧号严格对齐。

## 丢帧处理五步流程

官方《帧率问题分析》给出了处理丢帧问题的标准流程，共五步：

[图：丢帧问题处理流程图。识别卡顿（AppAnalyzer 体检）→ 查看建议（体检报告中的故障位置与优化建议）→ 分析原因（结合代码、Trace、调用栈）→ 选择优化方案（参考性能优化最佳实践）→ 验证优化效果（重新体检与录制 Trace 对比）。]

1. **识别卡顿**：先用 AppAnalyzer 检测滑动场景是否存在性能问题。AppAnalyzer 是 DevEco Studio 提供的检测评分工具，能自动完成编译、安装、运行和体检，输出体检报告。注意它的盲区：页面中视频播放或动画运行时存在补帧，此时对页面内的滑动组件（如视频播放页的评论区）做滑动检测，可能识别不出丢帧。
2. **查看建议**：体检报告会给出工具定位到的故障位置（如"UI 线程应用自身方法耗时长""组件未有效复用""图片纹理过大"）和对应的优化建议，方法名可以直接跳转源码。
3. **分析原因**：根据建议结合代码逻辑判断。工具给的是线索不是结论，需要结合 Trace 和函数调用栈确认。
4. **选择优化方案**：根据丢帧原因从性能优化最佳实践中选择对应手段——组件复用、懒加载、布局扁平化、状态精准更新、耗时操作移出主线程等。
5. **验证优化效果**：优化后重新体检、重新录制 Trace，对比丢帧率是否降到目标。验证这一步不能省，很多"优化"改完后指标没动，甚至引入新问题。

AppAnalyzer 走不通或者报告建议不够具体时，直接录制 Frame 模板 Trace 做深度分析，这就是 7.2 节案例的主线。

## 先排除系统侧，再查应用

打开一段丢帧 Trace，在钻进应用代码之前，有一个重要的前置步骤：确认应用线程的运行环境是否正常。官方流程把这个放在第一步——看线程状态和运行核，排除系统侧异常（出处：《帧率问题分析》）。

具体看两样东西：

**线程状态。** 在 CPU Core / Process 泳道中找到应用主线程在丢帧时刻的状态条。正常情况下丢帧处主线程大部分时间应该处于 Running 状态。如果看到的是频繁在 Running 和 Runnable 之间切换（说明在排队等 CPU）、或者频繁在 Running 和 Sleep 之间切换，那卡顿的原因可能不在应用代码，而在调度。

**运行核与频率。** 多核设备采用异构架构，区分大中小核。在 CPU Slice 和 Frequency 泳道上确认应用主线程是否运行在大核上、频率是否正常。官方文档给出的一个判读示例：某设备 0~3 号 CPU 为小核，4~11 号 CPU 为大核，丢帧处应用线程和前面正常帧一样运行在大核上，频率正常——据此排除系统异常，继续查应用。

如果出现以下现象，官方建议直接向系统侧提单反馈，而不是在应用代码里硬找：

- 执行频率较低；
- 关键线程在小核上工作；
- 线程频繁在 Running 和 Runnable 之间切换；
- 线程频繁在 Running 和 Sleep 之间切换；
- 不重要的线程占用了大核。

这一步的价值在于防止误判。同样的"应用帧超时"，可能是应用代码真的慢，也可能是主线程被别的进程抢了 CPU、被调度到小核低频运行。前者改代码，后者改什么都没用。花一分钟看线程状态和运行核，能避免在错误的方向上花几小时。

## 定界之后的分岔路

排除系统因素后，回到 Frame 泳道做定界：

- **App Frame 红**：审视 UI 线程的处理逻辑是否过于复杂或低效，是否被其他任务抢占资源。往下走应用侧 Trace：`H:FlushRenderTask`、`H:FlushDirtyNodeUpdate`、`H:FlushLayoutTask`、`Builder:BuildLazyItem`，配合 ArkTS Callstack 泳道找热点函数。这是应用开发者的主战场，7.2 节的案例走的就是这条路。
- **RS Frame 红**：审视界面布局是否过于复杂。借助 ArkUI Inspector 查看组件树嵌套层级，用 HiDumper 命令行 dump 渲染树信息，重点怀疑图层数量、大纹理、离屏渲染类效果（模糊、阴影、混合模式）。

两条路在第 13.2 节的 Trace 点速读表里都有对应的判读依据。

## 常见问题与误区

**"红帧就是我代码慢"。** 不一定。先看线程状态和运行核，再看红在哪一侧。RS 侧红帧时改应用代码是无效的。

**"丢一帧无所谓"。** 单帧超时 0.6ms 用户未必感知，但连续丢帧会累积成可见的卡顿。Profiler 的 Lost Frames 和 Hitch Time 子泳道专门统计连续丢帧数和卡顿时长，Hitch Time 的计算方式是渲染前后两帧的间隔减去单帧耗时，结果大于单帧耗时 70% 即视为卡顿（出处：《Frame 分析》）。看这两个指标比数红帧更接近用户体感。

**"首帧红就是有问题"。** 页面跳转后首帧需要重新加载和渲染全部新 UI 元素，渲染时间往往较长，首帧出现红色是常见现象，不一定表示存在严重性能问题（出处：《点击完成时延分析》）。但仍需关注首帧耗时，它是点击完成时延的组成部分，第 8 章会展开。

**"帧率够高就不卡"。** 平均帧率高不等于流畅。120Hz 设备上平均 118fps，如果那丢掉的两帧恰好连续出现，用户依然会感知到一次顿挫。看丢帧分布比看平均帧率更有意义。
