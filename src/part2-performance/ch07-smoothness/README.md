# 第 7 章：流畅性

流畅性是用户感知最直接的性能指标。滑动列表时画面跟不上手指、动画中间停顿一下、转场时闪了一下白屏，这些现象在系统层面都归结为同一件事：某一帧没有在它该出现的时间出现，也就是丢帧。

HarmonyOS 的图形系统采用统一渲染模式，应用侧负责生成界面描述，Render Service（RS）负责绘制合成并送显。这条流水线由 Vsync 信号驱动，60Hz 屏幕上一个周期 16.7ms，90Hz 是 11.1ms，120Hz 只有 8.3ms。任何一环在一个周期内没有做完自己的工作，用户就会看到一次卡顿。刷新率越高，留给每一帧的时间越短，对应用代码质量的要求也越苛刻。

本章解决两个问题：

**第一，看懂丢帧。** DevEco Profiler 的 Frame 模板把每一帧画成泳道上的色块，绿色是正常，红色是超时。系统在判定丢帧时区分责任方：应用侧没有按时提交渲染数据，记为 AppDeadlineMissed；Render Service 侧没有按时完成绘制，记为 RenderDeadlineMissed。这两类故障模型对应完全不同的排查路径，7.1 节讲清楚它们的判定逻辑、在 Trace 中的形态，以及官方推荐的"识别卡顿 → 查看建议 → 分析原因 → 选择优化方案 → 验证效果"五步处理流程。读完这一节，我们拿到任何一段 Frame Trace，都应该能回答三个问题：丢没丢、丢在哪一侧、下一步往哪里看。

**第二，动手查一次。** 7.2 节完整复盘官方"HMOS世界"应用的首页长列表丢帧案例：1000 条数据的列表滑动逐渐卡顿，用 AppAnalyzer 体检、用 Frame 模板录制 Trace，从 2.5 秒丢 16 帧的现象出发，一路追到 `BuildLazyItem` 耗时、`@Prop` 深拷贝和组件未复用这三个根因，再用 `@Reusable` 组件复用和 `@Builder` 修复，最后引用官方数据验证效果——组件复用前后丢帧率从 3.7% 降到 0%，`BuildLazyItem` 耗时从 10.277ms 降到 0.749ms（出处：《ArkUI 布局优化指导》）。这一节还会带出长列表场景的三个高频问题：布局嵌套过深、`cachedCount` 配置、主线程耗时操作。

丢帧分析是鸿蒙性能工作中复用价值最高的技能。本章建立的两个概念——App 侧与 RS 侧的定界、期望时间与实际时间的对比——会在第 8 章响应速度、第 13 章 Frame 模板 Trace 速读、第 14 章 DevEco Profiler 中反复用到。建议先读 7.1 建立模型，再跟着 7.2 动手做一遍，最后把第 13.2 节的 Trace 点速读表当作日常查阅的手册。

本章涉及的工具：AppAnalyzer（体检）、DevEco Profiler Frame 模板（深度分析）、ArkUI Inspector（布局层级检查）、HiTrace（命令行抓 Trace）。这些工具的完整用法在第三部分展开，本章只用到它们的丢帧分析能力。
