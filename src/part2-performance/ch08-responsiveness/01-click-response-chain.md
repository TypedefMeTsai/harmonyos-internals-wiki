# 8.1 点击响应链路与完成时延

## 为什么时延分析要先定义起止点

丢帧分析里，系统替我们做好了判定：每一帧有期望结束时间，超了就是红帧，Jank Type 也标好了。时延分析没有这种待遇。"这次点击慢"，慢多少？从哪算到哪？不先把起点和终点钉死，后续所有讨论都是空谈。同一个操作，从"手指落下"算和从"手指离开"算，结果能差出一百多毫秒；终点算"第一帧出现"和算"页面数据渲染完"，又能差出几百毫秒。

鸿蒙性能体系把一次点击拆成两个指标，各自有明确的起止点定义：

**响应时延**：起点是用户点击应用元素的时间（手指离手），终点是应用界面开始发生变化的时间。变化时间应控制在 100ms 以内，以保证操作响应及时（出处：《Web 点击响应时延分析》《应用时延优化案例》）。这个指标衡量的是"系统有没有立刻理我"。

**完成时延**：起点同样是用户输入触控指令，终点是界面完全刷新结束、达到可阅读的稳定状态。应用完成时延应 ≤900ms，元服务 ≤1400ms（出处：《应用性能体验建议》《点击完成时延分析》）。这个指标衡量的是"多久能开始用"。完成时延包含响应时延。

[图：点击完成起止点示意图。时间轴从左到右：手指按下、离手（响应时延与完成时延共同的起点）、界面开始变化（响应时延终点）、页面完全加载稳定（完成时延终点）。响应时延是完成时延的前缀。]

官方同时提醒：在一定时延水平以上，时延越短越好；但低于某个阈值后，用户的流畅体验不再继续提升。所以优化目标是达标并留有余量，而不是无限压低。

## 点击响应链路的五个环节

一次点击从硬件到屏幕，依次经过五个环节。理解每一环由谁负责、在 Trace 中叫什么名字，是时延定界的基础。

**1. 输入。** 触摸屏硬件产生中断，多模输入框架（multimodalinput）采集并分发事件。应用主线程收到事件，Trace 中的标志是 `H:DispatchTouchEvent`。点击离手那个事件（type=1）就是响应时延和完成时延分析的标准起点（出处：《点击完成时延分析》）。

**2. 主线程事件处理。** 应用的 onClick 回调、手势判定、状态变更逻辑在主线程执行。这一阶段是应用代码的第一现场：同步耗时函数、不合理的状态标脏范围，都会直接拉长这一段。

**3. UI 重建。** 状态变量变化触发组件标脏，下一个 Vsync 到来时执行重建：UpdateUI、Measure、Layout、Render，生成绘制指令。对应 Trace：`H:ReceiveVsync` → `H:OnVsyncEvent` → `H:FlushVsync` → `H:FlushDirtyNodeUpdate` → `H:FlushLayoutTask`。新页面场景还包括整棵组件树的创建（`initialRenderView`、`BuildLazyItem`）。

**4. RS 渲染。** 应用通过 `H:FlushMessages` → `H:SendCommands` → `H:MarshRSTransactionData` 把绘制指令提交给 Render Service，RS 侧执行 `H:ProcessCommandUni` 处理指令、GPU 绘制、合成。

**5. 上屏。** RSHardwareThread 提交合成结果给显示硬件，对应 Trace `H:RSHardwareThread::CommitAndReleaseLayers`。画面真正出现在屏幕上。

[图：点击响应链路时序图。五条横向泳道：输入系统、应用主线程、Render Service、硬件合成、屏幕。标出 DispatchTouchEvent（起点）、主线程事件处理段、FlushXXX 重建段、SendCommands 提交点、ProcessCommandUni、CommitAndReleaseLayers（上屏点）。]

## 各阶段的耗时基线

官方《点击响应时延分析》给出了首帧响应时延各阶段的划分和基线：

- **渲染阶段**（RS 侧）：起点是对应 RS 帧 `ProcessCommandUni` 的起点，终点是 `RSHardwareThread::CommitAndReleaseLayers` 的结束点，基线 20ms。
- **应用阶段**：开发者需要优化的主战场。若应用阶段耗时超过 25ms，加上机器硬件约 30ms 的耗时，整体时延可能超过 100ms，点击响应体验就不达标了。

这组数字值得记住：25ms + 30ms + 20ms 大约是 100ms 响应红线的全部预算，而应用阶段是其中唯一我们能改的部分。输入分发和硬件合成的耗时不受应用控制，优化响应时延本质上就是把主线程事件处理和 UI 重建压进 25ms 以内。

## 起止点在工具中怎么定

**起点**：录制 Frame 模板 Trace 后，搜索 `H:DispatchTouchEvent`，找到 type=1 的那一条（离手事件），它的时间戳设为起点。注意一次点击会产生按下（type=0）和离手（type=1）两条，别选错。

**响应时延终点**：界面开始变化没有统一的打点标志，实践中用录屏辅助——录屏工具逐帧找到界面第一次变化的帧，对照时间戳在 Trace 上标出。

**完成时延终点**：同样没有明确的 Trace 点，官方做法是通过录屏分析工具先算出完成时延的总耗时，再从起点往后拉相同的时间长度，找到终点位置（出处：《点击完成时延分析》）。

这种"录屏定终点、Trace 看过程"的组合是时延分析的标准姿势：录屏负责度量"多久"，Trace 负责解释"为什么"。DevEco Profiler 的 User Events 泳道也能辅助——它记录用户事件的开始时间（Input Time）、应用开始处理时间（Processing Start）和处理耗时（Duration），输入到应用接手的间隔一目了然。

## 完成时延的五类典型病因

官方《点击完成时延分析》把 AppAnalyzer 体检能检出的完成时延问题归为五类，这份清单可以作为排查时的核对表：

1. **UI 线程应用自身方法耗时长**：生命周期回调或事件处理里的同步耗时，典型如 aboutToAppear 里跑大循环、打海量日志。
2. **UI 线程应用自定义组件创建耗时长**：新页面组件树太大、单组件创建太贵。官方示例中一个自定义组件创建总耗时 40.933ms，直接吃掉一大块预算。
3. **网络请求耗时长**：分两种——请求本身慢（服务器或链路问题），和请求发起太晚（点击离手到请求发出的间隔长）。前者用预连接、预解析、CDN 优化；后者把请求提前发起。
4. **主线程长时间被阻塞**：主线程在等子线程任务、等系统接口返回、等 setTimeout。体检工具基于唤醒关系算法构建线程间依赖链路，能识别出阻塞主线程的子线程任务。
5. **图片大纹理**：源图尺寸远超组件显示尺寸，解码和上传耗时挤占帧预算。判据：尺寸大于 256×256 且超出组件尺寸 10%。

这五类里，前四类发生在第 2、3 环节（主线程），第五类横跨第 3、4 环节。定界方法不变：Trace 上从起点往后看，时间花在哪段，就是哪类。

## 网络请求的两个反模式

完成时延问题里，网络相关的占比很高，而问题往往不在网络本身，在请求的发起时机。官方文档点名两个反模式（出处：《点击完成时延分析》）：

**反模式一：在异步函数中发起网络请求。** ArkTS 是单线程 EventLoop 模型，异步调用的执行时机被推迟到同步逻辑之后。把 http 请求放在异步函数里，请求可能被 UI 绘制阻塞，等第一帧画完才开始。页面首帧越复杂，请求被推迟得越久。

**反模式二：在页面子组件中发起网络请求。** ArkUI 组件按树结构顺序创建。把请求放在某个子组件的回调里，它要排队等前面的兄弟组件创建完。文档给的例子：页面分 Header 和 Tabs 两部分，Tabs 数据的请求放在 Tabs 组件里发起，而 Header 的渲染又依赖网络——结果 Tabs 的请求被严重延后。

正确姿势：请求在页面创建的最早期（甚至点击发生的时刻）同步发起，UI 先渲染骨架，数据回来再刷新。8.2 节的案例会展示这类问题在 Trace 中的具体形态。

## 常见问题与误区

**"响应时延和完成时延一起优化"。** 两者的优化手段不同。响应时延看首帧，手段是减重：首帧少渲染、少执行。完成时延看全程，手段还包括动画时长、网络时序、数据分页。一个页面可以响应很快（骨架屏 50ms 出现）但完成很慢（数据 2 秒才回来），也可能反过来。

**"首帧红就是问题"。** 页面跳转的首帧要重建整棵树，超时是常见现象，不一定构成问题（出处：《点击完成时延分析》）。但首帧耗时计入完成时延，该压还是要压，只是不要看到红帧就当 bug 修。

**"时延是网络问题，客户端没法优化"。** 上面两个反模式说明，客户端能控制的是请求何时发出。把请求从"等 UI 就绪"提前到"点击即发"，经常能省出几百毫秒，比优化网络链路本身见效快。
