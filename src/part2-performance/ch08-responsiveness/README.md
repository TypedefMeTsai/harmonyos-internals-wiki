# 第 8 章：响应速度

第 7 章讲的是"动起来之后卡不卡"，本章讲的是"操作之后快不快"。用户点一个按钮，界面多久给出第一帧反馈？点一个条目，新页面多久完整呈现到可阅读状态？这两个问题分别对应鸿蒙性能体系里的响应时延和完成时延。

官方《应用性能体验建议》给出了明确的红线（出处：《点击完成时延分析》《时延体验建议》）：应用内点击操作响应时延应 ≤100ms，点击操作完成时延应用 ≤900ms、元服务 ≤1400ms。超过这条线，用户就会觉得"这应用反应慢"。响应速度问题和丢帧问题共用同一套渲染管线和同一批工具，但度量方式不同：丢帧看的是连续时间段内的帧质量，时延看的是一个操作从起点到终点的端到端耗时，先要定义清楚起点和终点，测量才有意义。

本章两节分别对应两类分析对象：

**8.1 点击响应链路与完成时延。** 把一次点击拆解成五个环节：输入事件 → 主线程事件处理 → UI 重建 → RS 渲染 → 上屏。每个环节在 Trace 中对应明确的打点：起点是 `H:DispatchTouchEvent`（type=1 表示离手），终点要靠录屏辅助标定。这一节讲清楚响应时延与完成时延的定义边界、起止点的取法，以及官方给出的各阶段耗时基线——比如首帧响应的 RS 渲染阶段基线 20ms，应用阶段超过 25ms 加上硬件约 30ms 就可能突破 100ms 的响应红线。

**8.2 转场时延分析与优化。** 页面跳转是完成时延问题最集中的场景。这一节按官方《点击完成时延分析》的定位流程展开：AppAnalyzer 体检确认时延超标，Profiler 抓 Trace 定起止点，然后沿四条泳道线排查——ArkTS Callstack 看应用函数耗时、Frame 看超长帧、ArkUI Component 看组件创建成本、H:Animator 看转场动画时长。官方案例的数据很能说明问题：Tabs 的 `animationDuration` 从 100ms 调到 1000ms，完成时延从 99ms39μs 直接涨到 1s7ms693μs；一个无效的单例创建销毁调用，在 ArkTS Callstack 上挂出 327ms。

读本章之前建议先读完第 7 章，Frame 泳道的判读方法（红绿帧、期望时间、定界）在这里会原样复用。工具侧的细节（Profiler 各泳道的完整操作）在第 14 章，本章聚焦"时延问题怎么想、怎么量"。
