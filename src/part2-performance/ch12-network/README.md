# 第 12 章：网络性能

网络是应用性能里最"身不由己"的一环：丢帧可以怪自己代码，网络慢可以怪信号、怪服务器、怪 DNS。但前面章节的分析已经反复表明，客户端可控制的部分远比想象中多——请求何时发出、连接是否复用、DNS 是否预解析、弱网时如何应对，这些决策影响的时延经常大于链路本身。

鸿蒙给应用提供两代 HTTP 客户端：`@ohos.net.http`（NetStack，API 6 起）和 `rcp`（RemoteCommunicationKit，API 11 起）。rcp 是新一代远程通信平台，在会话管理、自定义 DNS、HTTP 缓存、请求耗时追踪（timeInfo）上都比 http 模块完善，新代码应优先考虑 rcp。两者之上还有 Network Boost Kit 提供网络质量评估、场景识别（拥塞/弱信号预测）和连接迁移（Wi-Fi 与蜂窝互切）能力，让应用能对弱网做出主动反应而不是被动超时。

本章 12.1 节把网络栈的性能要点组织成四个问题：

1. **选型**：http 与 rcp 的能力差异，什么时候用哪个；
2. **测量**：一次请求的耗时怎么拆——rcp 的 timeInfo 把 DNS、TCP、TLS、发送、接收各段耗时直接交给应用，错误码里的 httpPhase 字段（如 111000 表示卡在 TLS 阶段）能定位失败发生在哪个阶段；
3. **优化**：连接复用与超时配置、自定义 DNS（dnsRules）、HTTP 响应缓存；
4. **弱网**：用 netQuality 订阅网络质量与场景变化，拥塞时降码率、连接迁移时快速重建。

学习这一节有个前置提醒：网络性能数据的方差天然很大，同一个请求在办公 Wi-Fi、地铁 4G、电梯里能差出两个数量级。所以本章的结论都要在"固定网络环境、多次采样取中位数"的前提下使用，单次抓包或单次计时得出的结论基本不可信。第 16 章方法论里"复现条件"一节对这类高方差问题有专门讨论。

网络问题在第 8 章（完成时延里的网络请求耗时）、第 22 章（请求、缓存与弱网策略实战）还会出现，本章负责讲清楚协议栈与 API 层面的性能事实。
