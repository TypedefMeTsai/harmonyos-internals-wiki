# 10.1 内存性能问题分类与排查路径

## 先分类，再动手

内存问题的排查效率，八成取决于开头的定性。三类问题在现象和打法上完全不同：

**OOM（内存溢出）**：申请内存时供给不足，应用直接崩溃或被系统杀死。特征是突发、致命、有明确的故障日志（jscrash 中的 Out of Memory 或资源耗尽类系统事件）。OOM 很少是"真的缺内存"，更多是长期泄漏或一次失控的分配（超大图片、无界缓存）把水用尽。

**泄漏（Leak）**：对象不再被使用，却因为残留引用无法被 GC 回收，内存占用只涨不回落。特征是锯齿消失、阶梯上升。官方最佳实践给出的典型判据：反复执行"进入页面 → 停留 → 返回"操作，正常预期是每次退出后内存回落至基线附近、整体呈锯齿状；实际异常是曲线阶梯状上升——某案例中多次操作后内存增长至 314.1MB 且无明显回落，即判定内存泄漏（出处：《ArkTS 内存泄漏场景化最佳实践》）。

**膨胀（Bloat）**：没有对象漏掉，但应用持有的内存结构性偏大——缓存不设上限、图片解码尺寸超标、每个页面各存一份全量数据。特征是基线水位高、GC 频繁、低端机上卡顿明显，但曲线能回落。膨胀不死人，却是一切内存问题的放大器：同样的泄漏速度，膨胀的应用先撞线。

[图：三条内存曲线对比。锯齿状（正常）、阶梯上升不回落（泄漏）、整体水位偏高但能回落（膨胀）。]

系统侧对泄漏有自动检测机制，可以作为判据参考：以应用进程平均动态峰值内存作为基线、200s 为基准窗口，动态内存峰值超过基线值 2 倍时判定泄漏并触发管控（PSS_MEMORY 类）；ASHMEM/DMA（ION）/GPU 等内核内存也有各自基线，超基线判定泄漏并抓取维测信息（出处：《资源泄漏检测》）。

## 两个视角：方舟 GC 与系统内存

**方舟运行时视角**：ArkTS 对象分配在虚拟机堆上，GC 按可达性回收。这个视角下的核心概念是引用链——对象收不掉，一定存在一条从 GC Root 到它的引用路径。工具是 Snapshot（堆快照）和 Allocation（分配追踪），回答的问题是"什么对象、被谁拽住、在哪分配"。

**系统视角**：进程在操作系统眼里是一组内存段。衡量指标是 PSS（按比例分摊共享页后的物理内存）和 RSS。构成上至少包括：native heap（C/C++ malloc）、ArkTS 堆、图形内存（Ashmem/DMA，图片纹理大头）、匿名页、映射的文件。这个视角的工具是 `hidumper --mem`，回答的问题是"内存总量多少、花在哪一类"。

两个视角必须配合：堆快照只能看到虚拟机堆里的对象，PSS 里的 native heap、图形内存它一概不知；反过来，PSS 涨也无法直接告诉我们是哪个 JS 对象。排查路径的第一原则就是**先用系统视角定层，再用对应层的工具定位**。

## 排查路径：定量 → 定层 → 定位

### 第一步：定量，确认问题的形态

拿 hdc 连上设备，对目标应用周期性采样：

```shell
hidumper --mem $(pidof 包名)
```

隔几秒执行一次，同时重复触发可疑场景（进出页面、滑动列表）。观察 Pss Total 的走势：锯齿状回落为正常，阶梯上升为泄漏，水位高但平稳为膨胀。输出中重点看两列（出处：《JSVM 内存泄漏定位》）：`native heap` 对应 Native 内存占用，`AnonPage other` 对应 JS 堆内存占用——这一步同时完成了定层。

### 第二步：定层，选择工具分支

- **JS 堆（AnonPage other）在涨** → 走 Snapshot 路线，查 ArkTS 对象。
- **native heap 在涨** → 走 native 路线：Allocation 模板的 native hook（采集堆内存分配调用栈，仅支持调试证书签名的应用），或检查 C++ 侧的 new/delete 配对、智能指针循环引用。
- **图形内存（Ashmem/DMA）在涨** → 怀疑图片：解码尺寸是否超过显示尺寸、Image 组件释放是否及时、是否有大图常驻。

### 第三步：定位，快照对比与泄漏检测

JS 层的标准动作是**两次快照对比**。DevEco Profiler 的 Snapshot 模板操作要点（出处：《Snapshot 模板基本操作》《ArkTS 内存泄漏分析》）：

1. 创建 Snapshot 会话，在可疑操作开始前拍第一份快照，重复操作若干轮后拍第二份。
2. 每次拍摄前虚拟机会触发 GC，所以快照里存留的对象理论上都是 GC 收不掉的——这天然过滤了噪音，留下的差值就是嫌疑对象。
3. 在 Comparison 区域选一份为 base、另一份为 Target 做对比，比较内容包括新增数、删除数、个数增量、分配大小（Alloc Size）、释放大小（Freed Size）、大小增量（Size Delta）。
4. 按大小增量排序，找"新增且不释放"的对象类型，再用 Containment 视图（自上而下的引用树）沿引用链找到拽住它的那个根——通常是忘了反注册的监听器、静态集合、未关闭的回调。

要拿到分配点的调用栈，用 **Allocation 模板的泄漏检测**：创建 Allocation 会话、添加 ArkTS Snapshot 泳道、开启泄漏检测配置，录制泄漏场景，工具直接给出泄漏对象对应的调用栈（出处：《ArkTS 内存泄漏总览》）。

Snapshot 还有两个实用细节：支持离线导入 `.heapsnapshot` 文件（Profiler 会话区 Open File），方便分析别人抓的现场；Statistics 视图用饼图展示各类型对象的内存占比，适合快速看结构。Native 侧可以调 `OH_JSVM_TakeHeapSnapshot` 主动拍快照——注意它会短暂暂停应用运行，且回调在 VM 线程同步执行，不要做阻塞操作（出处：《JSVM 堆内存管理》）。

## 与其他章节的衔接

内存问题很少孤立存在。PSS 长期高位会提高进程被系统回收的概率（第 4 章的内存压力治理）；堆膨胀导致 GC 频繁，表现为间歇性卡顿甚至 THREAD_BLOCK（第 9 章根因表里的"触发长时间 GC"和"触发长时间抓取内存快照"——注意，拍堆快照这个动作本身在主线程重负载时也能诱发 AppFreeze，线上慎用）；图片大纹理既是内存问题也是丢帧问题（第 7 章体检报告里的图片大纹理项）。排查时如果发现内存问题的代价主要体现在卡顿上，回到第 7 章的方法度量它。

## 常见问题与误区

**"PSS 涨就是泄漏"。** PSS 包含共享库、字体、系统映射的摊销，启动后自然爬升一段才稳定。判泄漏看的是"重复操作后的增量是否回落"，不是绝对值。

**"堆快照里有就是泄漏"。** 快照里所有对象都是"GC 收不掉的"，其中大量是合理存活（缓存、单例）。泄漏判定的依据是两份快照间"新增且不释放"的对象，以及引用链是否指向意外的持有者。

**" GC 都收不掉，一定是框架 bug"。** 绝大多数 ArkTS 泄漏的原因平淡无奇：监听器没反注册、全局 Map 只增不减、闭包持有大对象。先在业务代码里找引用链，框架嫌疑放最后。
