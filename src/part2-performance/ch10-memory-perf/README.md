# 第 10 章：内存性能

内存问题在鸿蒙应用上的表现形式很多样：操作几轮之后应用越来越卡（内存膨胀挤压 GC），反复进出某个页面后闪退（泄漏累积到 OOM），后台切前台发现应用被杀了（内存水位高被系统回收）。它们共享同一个根源：应用的内存占用与系统的供给之间失去了平衡。

鸿蒙应用的内存视角是双层的。底层是系统视角：进程占多少物理内存（PSS/RSS），系统剩余多少，什么时候触发回收——这部分由内核和系统内存治理机制决定。上层是方舟运行时视角：ArkTS 对象活在虚拟机堆里，由 GC 管理生死，泄漏在多数情况下是"对象被意外的引用链拽住，GC 收不掉"。两个视角的排查工具和思路完全不同，而很多内存问题之所以难查，是因为排查者在错误的层用了错误的工具——拿着堆快照去找 native 泄漏，或者盯着 PSS 曲线去猜 JS 对象。

本章 10.1 节先把问题分清楚：OOM、泄漏、膨胀三类内存问题各自的特征曲线长什么样；然后给出"先定量、再定层、后定位"的排查路径——用 `hidumper --mem` 看 PSS 构成判断问题在 native 层还是 JS 堆，用 Snapshot 堆快照对比定位 JS 对象，用 Allocation 模板的泄漏检测拿调用栈。官方给出的资源泄漏检测机制（动态峰值内存超过基线 2 倍判泄漏）和一个"反复进出页面内存阶梯式涨到 314.1MB 不回落"的真实案例也会在这一节展开。

读这一节之前，建议先回顾第 4 章的方舟运行时内存模型——GC 的可达性判定、堆的分代结构，是理解"对象为什么收不掉"的前提。读完之后，第 14.3 节的 Snapshot 与 Allocation 会话操作可以当作配套实验手册：10.1 节讲怎么想，14.3 节讲每个按钮在哪。

内存优化的具体手段（图片内存、组件释放、缓存策略）放在第五部分第 21 章，本章只负责把"诊断"这一步做扎实：面对一个内存问题，知道它属于哪类、在哪一层、下一步拿什么工具。
