# 写在前面

这本书回答一个问题：**当你手上的鸿蒙应用卡了、慢了、冻了、耗电了，你怎么知道问题出在哪一层？**

HarmonyOS 从 4.x 的双框架时代走到 NEXT（5.x）再到 6.x，应用栈从"能跑"变成了"必须跑好"。生态里的应用越来越多，体验红线也越来越硬：滑动帧率、点击响应、启动速度、应用无响应率、功耗，每一项都有明确的验收口径。但大多数开发者面对性能问题时，手里只有两样东西：DevEco Studio 里一条红色的帧，和一句"优化一下"。

这本书想把中间缺的那段补上：

- 系统机制：ArkUI 怎么把声明式描述变成像素，Render Service 怎么送显，Vsync 怎么对齐整条管线，TaskPool 和 Worker 到底差在哪，应用无响应是怎么被判定的。
- 分析方法：问题现象对应哪类故障模型，用 hitrace 还是 Profiler，看到 Trace 之后怎么读，怎么把一次调查写成能复查的证据。
- 优化实践：启动、渲染、内存、I/O、功耗、包体积，应用团队能改什么，怎么验证改对了。

写法和结构移植自姊妹项目《Android 技术内幕》（android-internals-wiki）：机制说明带 OpenHarmony 源码路径，工具章讲采集与证据形态，实践章讲应用团队能落地的改法。有 Android 系统分析经验的读者会发现两条技术栈在"渲染管线怎么组织、丢帧怎么归因"上的思路高度相通，书里在必要处做一次性类比，其余地方都用鸿蒙自己的术语。

## 素材来源

- 华为开发者官方文档与最佳实践（developer.huawei.com）：性能体检建议、帧率问题分析、丢帧故障模型、Profiler 会话说明等。
- OpenHarmony 开源主干：`graphic_graphic_2d`（Render Service）、`arkui_ace_engine`（ArkUI Engine）、`arkcompiler_ets_runtime`（方舟运行时）等仓库。
- 公开发布的 HarmonyOS 版本说明与 API 参考。
