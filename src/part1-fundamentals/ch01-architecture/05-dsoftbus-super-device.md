# 1.5 分布式软总线与超级终端

## 为什么需要软总线

用户手里不只有一台设备：手机、平板、手表、车机、智慧屏。如果这些设备两两之间都要应用自己去发现、配对、建连、维护心跳、协商加密，那"跨设备"就只是口号。分布式软总线（Distributed SoftBus）把这件事做成了系统级基础设施：**对上提供统一的设备发现、连接、传输接口，对下屏蔽 Wi-Fi、蓝牙、星闪等不同物理链路的差异**。应用在跨设备场景下调用的接口，和本机接口长得几乎一样。

软总线之上长出来的用户可感知能力，就是超级终端（控制中心里拖动设备卡片组网的交互）、应用流转、跨设备剪贴板、华为分享等。官方术语表对超级虚拟终端（即超级终端）的定义是：通过分布式技术将多个终端的能力整合，存放在一个虚拟的硬件资源池里，根据业务需要统一管理和调度终端能力，对外提供服务。

## 四层结构：发现、连接、组网、传输

软总线（OpenHarmony 仓库 `foundation/communication/dsoftbus`）自底向上分四层，每一层解决一个问题。

**发现层**回答"附近有谁"。通过 CoAP 广播（局域网）和 BLE 广播两种通道交换设备名片（设备类型、能力、账号信息摘要）。两台设备要在同一局域网或同时打开蓝牙，才能互相发现。设备管理模块（DeviceManager）把发现结果上报给框架层，应用看到的"附近设备列表"就来自这里。

**连接层**回答"能不能信得过"。发现的设备分可信与不可信：同账号设备靠账号体系自动互信；不同账号设备要走绑定流程——官方设备管理文档列出的认证方式包括 PIN 码、碰一碰、扫码、靠近。绑定成功后双方建立可信关系，协商出会话密钥，后续通信加密。连接层还负责在多条物理链路里选路：Wi-Fi P2P 带宽高、蓝牙功耗低，软总线按业务类型（控制信令走蓝牙，大数据走 Wi-Fi）自动选择。

**组网层**把已认证、已连接的设备组织成一个逻辑网络，维护成员上线/下线事件。组网成功后，每台设备拿到对端的 networkId——这是之后所有跨设备调用的地址。分布式文件系统的文档给了一个直观的体验描述：组网下文件一端创建、删除、修改，另一端可以"立即"看到，速度取决于网络情况。

**传输层**提供四种数据通道：字节流（低延迟小数据）、消息（可靠小包）、文件（大文件传输，支持断点）、流（音视频实时流）。应用开发中常用的是消息与文件通道；跨设备 IPC（下文）走的是字节/消息通道。

## 跨设备 IPC：dbinder

1.4 节说过，鸿蒙的 IPC 在本机走 binder。跨设备时，同一套调用语义由 **dbinder**（distributed binder）延续：客户端拿到的代理对象背后不是本机 binder 驱动，而是软总线的传输通道；调用消息被序列化后经软总线发到对端，对端交给本地的服务实现，结果原路返回。对应用框架而言，"调本机的服务"和"调对端设备的服务"是同一套代码路径。

这条链路解释了跨设备调用的性能特征：本机 IPC 是微秒到亚毫秒级，跨设备 IPC 则取决于传输层走的链路——同局域网 Wi-Fi 下是毫秒级到十几毫秒，蓝牙通道更慢。所以跨设备调用**不适合放在交互热路径上**（比如每帧调用），官方多端协同的示例也都把它用在"拉起对端 Ability、传控制信令"这类低频动作上，数据面（视频流、文件）走专门的流/文件通道。

## 应用流转与多端协同

软总线之上，应用层能直接用的分布式能力主要有三类：

- **跨端迁移**：正在使用的 UIAbility 连同页面状态迁到另一台设备继续（手机上看的文章，靠近平板后在平板上接着看）。本质是源端保存页面状态快照，经软总线传到目标端恢复。
- **多端协同（startAbilityByCall）**：本端拉起对端设备的 Ability 并保持一个 Call 会话，双方可互调方法。官方分布式数据对象文档给了标准流程：先 `genSessionId` 拿会话号，通过设备管理接口取对端 networkId，组装进 want，调 `startAbilityByCall` 拉起对端，然后双端创建分布式数据对象加入组网，数据变更自动同步。
- **系统推荐流转**：环境中存在体验更优的设备时，系统主动向用户推荐流转目标（术语表中的 System suggested hop）。

## 实际工作中怎么用

**确认组网是否成功：**

```bash
hdc shell "hidumper -s 4700 -a \"buscenter -l remote_device_info\""
```

组网成功时输出里能看到 `remote device num = 1` 之类的对端设备数量（SAID 4700 是软总线 buscenter 的系统能力号）。跨设备功能"没反应"时，这是第一条该跑的命令——先确认两台设备到底组上网没有，再怀疑应用逻辑。

**跨设备问题排查顺序**：发现失败 → 查两台设备是否同局域网/蓝牙都打开；连接失败 → 查绑定状态（同账号免绑定，跨账号要走认证）；组网成功但调用超时 → 查链路质量，分布式文件系统文档里提到过一个典型现象：设备离线感知有延迟，部分消息会有约 4s 超时，开发者要对接口网络超时做容错。

**性能建议**：跨设备传输大文件用文件通道而不是自己分包发消息；实时音视频用流通道；控制信令用消息通道。选错通道（比如用消息通道传图）会在弱网下放大延迟。

## 版本演进

- API 9–11：软总线能力以系统应用（超级终端、多屏协同）为主，三方应用可用 DeviceManager 做发现与绑定；
- API 12（5.0）：分布式数据对象、跨设备 Call 调用等面向应用的多端协同能力完善，LinkEnhance（增强连接）接口开放；
- API 20+（6.0）：官方全场景协同章节把能力收敛为一次开发多端部署、接续、跨设备互通、跨设备剪贴板、键鼠共享、无线投屏、华为分享等场景化接口，并新增碰一碰分享、隔空传送等交互；星闪（NearLink）链路进入软总线传输层选项。

## 常见问题与误区

**"超级终端是应用层功能"。** 不是。它是软总线组网能力在控制中心的一个 UI 入口，背后是整个发现—连接—组网—传输栈。应用不接入任何 SDK 也能被拖进超级终端，前提是声明了分布式相关能力。

**"跨设备调用和本机调用一样写就一样快"。** 接口同构不等于性能同构。把跨设备 IPC 放在每帧执行的路径上，是分布式应用最典型的性能事故。
