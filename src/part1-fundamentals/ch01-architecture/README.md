# 第 1 章：系统架构全景

性能问题很少是孤立发生的。一个滑动丢帧，可能出在 ArkUI 的状态刷新，也可能出在 Render Service 的合成，甚至可能出在另一个进程里某个系统服务没有及时响应 IPC。如果我们脑子里没有一张系统全景图，拿到一段 Trace 时就只能看到孤立的泳道，看不出彼此之间的因果关系。

本章的任务就是把这张图画出来：鸿蒙系统自下而上分哪几层、每一层有哪些常驻进程、应用进程是怎么被拉起来的、系统服务是怎么注册和被找到的、跨设备调用走的是哪条路。读完这一章，我们应该能在 hdc shell 里回答这几个问题：当前设备跑的是什么内核、某个系统服务由哪个进程承载、我的应用有几个进程、对端设备是怎么被发现的。

## 各小节地图

- **1.1 四层架构与内核可替换设计**：内核层、系统服务层、框架层、应用层分别管什么；为什么同一套 ArkTS 代码能跑在 LiteOS-M 的表和 Linux 内核的手机上；内核抽象层在这件事里扮演的角色。
- **1.2 OpenHarmony 与 HarmonyOS 的关系**：开源项目和商用发行版的分工，API 版本从 9 到 20+ 的演进脉络，以及"双框架"时代的结束意味着什么。读源码之前先读这一节，知道哪些机制能直接对照 OpenHarmony 仓库、哪些只能以官方文档为准。
- **1.3 Stage 模型、Ability 与进程模型**：应用侧的基本单元。UIAbility 生命周期、module.json5、HAP 包结构，以及"默认一个应用一个进程"这条规则和它带来的性能含义。
- **1.4 系统服务框架：SAMgr、init 与进程骨架**：从开机到应用启动之间发生了什么。init 拉起服务骨架，SystemAbilityManager 维护系统服务注册表，应用通过 IPC 找到服务。后面所有"系统服务没响应"类的问题都要回到这一节的模型。
- **1.5 分布式软总线与超级终端**：发现、连接、组网、传输四层如何工作，跨设备 IPC 和应用流转建立在什么之上。

## 阅读顺序

按 1.1 → 1.5 顺序读即可。1.1、1.2 偏概念，建立坐标系；1.3、1.4 偏机制，是理解本书第二部分性能案例的前提；1.5 相对独立，做跨设备场景时再细读也不迟。如果读者来自 Android 背景，可以把 1.4 的 SAMgr 类比 SystemServer 加 ServiceManager，把 1.5 的软总线类比一条跨设备的 binder 通道，但请注意这只是入门的类比，具体机制差异不小，正文会逐一说明。
