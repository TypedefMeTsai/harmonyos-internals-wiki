# 1.1 四层架构与内核可替换设计

## 为什么要先谈分层

我们看一段性能 Trace 时，看到的从来不只是"应用"。一条输入事件要从内核的 input 子系统出发，经过多模输入服务、窗口管理，才到达应用进程；一帧画面要从应用的 ArkTS 代码出发，经过 ArkUI 框架、Render Service 进程、GPU、硬件合成器，才出现在屏幕上。如果我们不知道鸿蒙系统自下而上分哪几层、每一层有哪些常驻模块，就只能在 Trace 里看到一堆互不相干的泳道。

鸿蒙官方把系统划分为四层：内核层、系统服务层、框架层、应用层。这个划分不是 PPT 上的装饰，它直接对应着设备上真实存在的进程边界和代码仓库边界，也解释了鸿蒙最有辨识度的一个设计——内核可替换。

[图：四层架构示意图。最底层为内核层（LiteOS-M / Linux / HarmonyOS Kernel 三个并列方框，上方覆盖一层 KAL 内核抽象）；其上为系统服务层（基础软件服务子系统、增强软件服务子系统、硬件服务子系统，标注关键进程：samgr、foundation、render_service、appspawn）；再上为框架层（ArkUI、ArkCompiler Runtime、Ability 框架、ArkData、ArkWeb，标注运行在应用进程内）；最上为应用层（系统应用与三方应用，每个应用一个或多个进程）。层与层之间用箭头标注调用方向：上层调用下层，跨层调用经 IPC 或 NDK。]

## 四层分别管什么

**内核层**负责进程调度、内存管理、文件系统、设备驱动，以及为上层提供 POSIX 风格的系统调用接口。鸿蒙的特殊性在于这一层不是一个固定内核，而是一组可替换的内核实现，上面盖着一层内核抽象（KAL，Kernel Abstraction Layer）。

**系统服务层**是系统能力的实体。窗口管理（WMS）、包管理（BMS）、应用管理（AMS 对应的 AbilityManagerService）、图形渲染（Render Service）、分布式软总线、多模输入等，都以独立进程或进程内线程的形式常驻运行。每个能力在系统里注册为一个 SystemAbility（SA），由 SystemAbilityManager 统一管理——这是 1.4 节的主题。

**框架层**是给应用开发者用的 API 集合：ArkUI（声明式 UI）、ArkCompiler Runtime（方舟运行时）、Ability 框架（Stage 模型）、ArkData（数据管理）、ArkWeb 等。注意框架层大部分代码运行在**应用进程内**——我们的 ArkTS 代码、ArkUI 框架代码、方舟运行时，都链接在同一个进程里；它们需要系统能力时，再通过 IPC 调用系统服务层的对应进程。这个"框架在应用进程内、能力在系统进程内"的边界，是分析跨进程开销时的基本坐标。

**应用层**就是系统应用和三方应用。每个应用默认运行在自己的沙箱进程中（见 1.3 和 6.1 节）。

## 内核可替换：为什么会有三种内核

鸿蒙要覆盖的设备跨度极大：一边是内存只有几百 KB 的 MCU 设备（传感器、智能家居模组），一边是内存十几 GB 的手机和 PC。没有一个内核能同时适配这两个极端，所以内核层按设备形态做了三档：

- **LiteOS-M**：面向轻量设备（mini system，百 KB 级内存）的微内核实现，运行在 MCU 上，没有 MMU。
- **Linux 内核**：面向标准设备（standard system，手机、平板、车机）的完整内核，提供完整的进程隔离、虚拟内存和驱动生态。我们日常调试的华为手机，内核层就是它。
- **HarmonyOS Kernel（鸿蒙内核）**：华为自研内核，在 HarmonyOS NEXT（5.0，API 12）之后的商用旗舰设备上逐步替换 Linux 内核的位置。[待验证：具体机型与版本的内核切换时间表，官方未公开完整清单]

三个内核之上是 KAL 内核抽象层。系统服务层的代码不直接调内核特有的接口，而是调 KAL 定义的统一接口（线程、定时器、内存、IPC 原语等），由 KAL 把调用翻译给当前设备上实际存在的内核。这样系统服务层及以上的所有代码都不关心自己跑在哪个内核上。

## "一次开发多端部署"为什么依赖内核抽象

我们经常把"一次开发，多端部署"理解成 UI 自适应（一套 ArkTS 页面适配不同屏幕），但 UI 自适应只是最上面一层。真正让同一套代码能跑在不同设备上的，是自下而上的一串抽象：

1. 内核抽象（KAL）抹掉了 LiteOS-M 和 Linux 的差异，系统服务层代码一份编译多处运行；
2. 系统能力（SystemCapability，SysCap）机制让每个设备声明自己支持哪些能力，应用安装和运行时按 SysCap 判断功能可用性，而不是按设备型号硬编码；
3. 框架层 API 按 SysCap 组织，同一个 ArkTS 接口在有硬件和没硬件的设备上表现出定义好的行为（可用或返回特定错误码）；
4. 最上面才是 UI 层的断点、栅格和响应式布局。

没有第 1 条，后面三条都不成立。所以"一多"不是应用层的技巧，而是从内核抽象开始的一整套设计。

## 实际工作中怎么用

**确认当前设备的内核。** 在标准系统设备上：

```bash
hdc shell "cat /proc/version"
hdc shell "param get const.product.software.version"
```

`/proc/version` 存在且返回 Linux 版本信息，说明内核层是 Linux 内核；鸿蒙内核设备上该命令的行为会有差异。[待验证：HarmonyOS Kernel 设备上 /proc/version 的具体输出]

**确认设备支持的系统能力。** 分析"为什么这个 API 在 A 设备能用、B 设备报错"时，先查 SysCap：

```bash
hdc shell "cat /system/etc/syscap.json" | head -50
```

应用侧则用 `canIUse("SystemCapability.XXX")` 在运行时判断，比按设备型号写 if-else 可靠得多。

**理解性能分析中的进程边界。** 拿到 Frame 模板 Trace，应用进程泳道里的 `H:MarshRSTransactionData` 是框架层（应用进程内）的产物，`render_service` 泳道是系统服务层的进程，`PresentFence` 则来自内核层驱动的显示子系统。一个丢帧问题横跨了三层，定位时先确认卡在哪一层，再往下钻，这是第二部分所有案例的共同开场。

## 版本演进

- OpenHarmony 早期版本（API 8 及之前）的"一多"能力较弱，内核抽象主要服务于轻量与标准两类系统的代码复用。
- HarmonyOS NEXT / 5.0（API 12）起，商用设备转向单框架（见 1.2 节），鸿蒙内核开始在旗舰机型上替代 Linux 内核，内核抽象层从"支持多内核"进一步变成"支撑内核替换"的关键路径。
- 到 HarmonyOS 6.x（API 20+），官方技术白皮书把四层架构表述为"软硬芯垂直整合"的一部分，内核层与芯片的协同调度（如 FFRT 对大小核的感知，见 5.3 节）成为新的优化方向。

## 常见问题与误区

**"鸿蒙就是 Linux"或者"鸿蒙不用 Linux 了"，两种说法都过于简化。** 内核层是可替换设计：标准系统设备长期以 Linux 内核为主，5.0 之后旗舰设备引入鸿蒙内核，轻量设备一直是 LiteOS-M。讨论问题时要先限定设备和版本。

**框架层代码不等于系统代码。** ArkUI 框架 crash，崩溃日志落在应用进程；Render Service crash，落在系统侧。报障时分清这一点，能省掉大量扯皮时间。
