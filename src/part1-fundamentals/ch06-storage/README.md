# 第 6 章：存储与 I/O

应用的持久化需求看着简单——存点配置、存点数据——但鸿蒙给的不是一个"文件系统随便读写"的环境。应用被关进沙箱，只能看到自己的目录视图；配置数据有 Preferences，结构化数据有关系型数据库，跨设备同步有分布式数据服务，各有各的适用边界和性能脾气。选错存储方案的代价很具体：往 Preferences 里塞大 JSON，启动时全量加载直接拖慢冷启动；在主线程同步查库，列表页一进来就丢帧；该走 Picker 的用户文件偏要拼路径，权限报错还查不到原因。

本章两节：第一节讲文件——沙箱里的目录结构、三类文件的视图隔离、路径怎么映射；第二节讲结构化存储——Preferences、KV-Store、RDB 三套机制怎么工作、各自适合什么、怎么避开性能坑。存储问题排查的通用套路（先看路径对不对、再看线程对不对、最后看选型对不对）会反复出现。

## 各小节地图

- **6.1 应用沙箱与文件系统视图**：为什么应用看不到真实物理路径；应用文件、用户文件、系统文件三类对象的不同访问方式；el1/el2 加密等级与目录布局；文件操作放错目录、放错线程的实际后果，以及 Native 侧获取沙箱路径的正确方式。
- **6.2 Preferences、KV Store 与关系型数据库**：三套机制的存储模型、性能特征与选型规则；Preferences"全量加载内存"意味着什么；KV-Store 的分布式同步走哪条通道；RDB 的异步、事务、索引三条纪律。

## 阅读顺序

先 6.1 后 6.2。文件视图是基础概念，结构化存储都落在沙箱的 database 和 preferences 目录下，路径概念会反复用到。第 22 章的 I/O 与序列化优化案例以本章为机制基础；涉及跨设备数据同步时，需要回头对照 1.5 节软总线的链路约束——分布式数据服务的数据通道建立在软总线组网之上，组网不通时一切同步免谈。两节末尾的选型速查表和排查清单可以直接当 Checklist 用。
