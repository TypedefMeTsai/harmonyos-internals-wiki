# 第 3 章：输入系统

输入是性能的起点：用户手指落下的那一刻，计时就开始了。点击响应时延、滑动跟手性、手势冲突——这些问题的答案都藏在"事件从哪里来、经过谁、在什么时刻被处理"这条链路上。

鸿蒙把触屏、鼠标、键盘、手写笔、触控板、手柄统一收进多模输入框架，再把事件交给窗口和 ArkUI 的渲染管线处理。输入系统和第 2 章的渲染系统是咬合在一起的：触摸事件在一帧的 Events 阶段被分发，事件回调里改的状态在同一帧的 UpdateUI 阶段生效，下一帧变成像素。理解了这条时间线，"为什么主线程卡一下用户立刻觉得不跟手"就是可以直接推导的事实，而不是玄学。

这一章不涉及复杂工具，更多是把因果链讲清楚：响应链怎么建立、事件在哪一帧被处理、手势之间谁赢谁输。链清楚了，第 8 章的响应时延案例才能看懂每一步在等什么。

## 各小节地图

- **3.1 多模输入框架与事件分发**：事件从内核 input 子系统到应用组件的完整分发链，多模输入服务的角色，以及怎么用注入事件的方式做自动化验证。"点了没反应"类问题的分层排查顺序也在这一节。
- **3.2 触摸响应链与跟手性**：触摸测试如何建立响应链、hitTestBehavior 如何改变事件走向，跟手性的官方标准（抛滑 ≤80ms、拖滑 ≤60ms）背后是哪几段时间——硬件采样、排队等 Vsync、事件回调与布局、RS 绘制送显。
- **3.3 手势识别与系统手势导航**：ArkUI 手势识别器的工作方式、手势组之间的竞争规则（互斥/并行/顺序），gesture 与 priorityGesture 的区别，以及应用手势与系统导航手势冲突时的三类处理思路。

## 阅读顺序

3.1 建链路，3.2 讲时间，3.3 讲竞争。做响应速度优化（本书第 8 章）之前，至少要把 3.1 和 3.2 读完；列表、Tabs、抽屉类交互出现手势问题时，直接翻 3.3 的冲突案例对照。来自 Android 背景的读者可以把多模输入服务类比 InputReader/InputDispatcher 的合体，但事件进入应用后的处理方式不同——鸿蒙把输入分发收进了渲染管线的帧节拍里，这个差异是理解鸿蒙跟手性问题的钥匙。
