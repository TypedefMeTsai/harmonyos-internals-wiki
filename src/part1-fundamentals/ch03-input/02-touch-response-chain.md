# 3.2 触摸响应链与跟手性

## 手指落下之后，事件给谁

屏幕上同一坐标点可能叠着好几层组件：页面、卡片、按钮、按钮里的图标。一次按下，到底谁的 `onTouch` 被调用？答案由**事件响应链**决定，而响应链由**触摸测试**（hit test）建立。

官方交互机制文档描述了完整过程：管线接收到起始触控事件（Down）后，根据事件坐标和各组件的位置进行触摸测试，自顶向下找出所有命中该点的组件，按"最内层组件在前"的顺序串成事件响应链。之后的 Move、Up 事件不再重新测试，沿着 Down 建立的链分发——所以"按下在按钮上、滑出按钮再抬起"，事件依然属于按钮。

事件在链上的默认传递规则（NDK 事件文档的表述）：从最内层组件优先处理，再逐层向父组件传递，任意一层可主动终止传递。手势识别也挂在这条链上——链上每个节点注册的手势识别器参与竞争（3.3 节）。

## hitTestBehavior：改变响应链的形状

组件的 `hitTestBehavior` 属性控制它自身如何参与触摸测试，官方多层级手势文档用的例子很直观：组件 A（父）叠着组件 B 和 C，D 又在 C 上。当 C 设置 `HitTestMode.BLOCK_DESCENDANTS` 时，点 B/D 重叠区域，A 和 B 的 onTouch 触发，C 和 D 收不到，B 的点击手势生效。四种模式的行为：

- `Default`：自身和子节点都参与，正常入链；
- `Block`：自身命中，阻断兄弟节点中排在它后面的（下层兄弟收不到）；
- `BlockDescendants`：自身命中但阻断所有后代——上面的例子；
- `None`：自身不参与，后代可参与（"透视"容器）。

实践建议官方也说清楚了：简单场景在单个组件上设置；复杂场景在多个组件上组合不同模式来控制分发。排查"点不动"时，先看命中路径上有没有谁设了 Block 类模式——盖了一层透明但参与命中的容器，是最常见的遮挡事故。

## 跟手性：从手指到像素的时间账

跟手性是用户对"滑得流不流畅"的直觉评价，官方把它量化成了响应时延标准（性能体验文档）：**抛滑（速度大于 300mm/s）场景触屏响应时延应 ≤ 80ms；拖滑（速度小于 100mm/s）场景应 ≤ 60ms**。

这笔钱花在哪？把 3.1 的链路和 2.2 的帧模型拼起来，一次触摸移动的端到端时间是这几段的和：

1. **硬件采样**：触控 IC 按报点率采样，120Hz 报点约 8.3ms 一个点；
2. **多模加工与跨进程投递**：微秒到毫秒级；
3. **排队等 Vsync**：事件到应用进程后要等下一个 Vsync 的 Events 阶段才被分发，最坏情况排一个帧周期（120Hz 下 8.3ms）；
4. **事件回调 + 状态更新 + 布局**：Events 回调改状态，同一帧 UpdateUI/Measure/Layout 生效——主线程越忙这段越长；
5. **RS 绘制与送显**：再等一个 Vsync 周期由 render_service 消费（2.2 节）。

也就是说，理想情况下手指移动到画面更新要约 1.5～2 个 Vsync 周期加硬件采样时间；120Hz 下约 20ms 出头。预算的余量都留给第 4 段——**主线程一旦单帧超时，跟手性立刻恶化**，因为事件分发本身就被堵在排队里。这就是"滑动时主线程卡一下，用户立刻觉得不跟手"的物理原因。

## 实战：跟手性问题怎么查

**第一步，确认是真丢帧还是假丢帧。** Frame 模板里滑动区间没有红帧，但用户觉得不跟手，查手势阈值：PanGesture 的 `distance`（最小触发距离，默认 5vp，手写笔 8vp）设太大，手指滑出去一截列表才动——官方 PanGesture 文档明确提醒"滑动距离设置过大会导致滑动不跟手"。这种是识别延迟，不是渲染丢帧。

**第二步，看 Events 阶段是否在等。** Trace 上输入事件的分发点与 Vsync 起点之间的间隔长，说明主线程前一帧没收尾，事件在排队——根因在前一帧的超时段，按第 7 章的丢帧分析走。

**第三步，看事件回调里干了什么。** onTouch 的 Move 回调是每报点一次就调一次的热路径，在里面做布局无关的重计算、打高频日志、同步 IO，都会把第 4 段拉长。该采样降频就降频（比如每 2～3 个点处理一次，或直接用历史点接口批量取）。

**第四步，确认动画类型。** 跟随手指的动效用 animator（帧动画）实现时，每帧要在应用侧算值，主线程负载直接叠加；能换成属性动画/手势驱动动画就换，让 RS 侧插值（2.1 节）。

## 常见问题与误区

**"提高触摸采样率就能更跟手"。** 采样率只决定输入密度，决定不了排队和渲染时间。主线程 20ms 一帧时，240Hz 报点只是让队列里多积几个事件。

**"onTouch 里 stopPropagation 能解决一切冲突"。** 终止传递只影响 Touch 事件的链上分发，不影响手势识别器之间的竞争规则（那是 3.3 节的另一套机制）。混用两套手段是手势 bug 的常见来源。

**响应链在 Down 时定死这件事常被忘掉。** 想在滑动中途把事件"转手"给另一个组件，标准做法不是改响应链，而是用手势协调（手势组、嵌套滚动）或在中途主动构造事件。

## 版本演进

- API 9–11：触摸测试与响应链机制随 ArkUI NG 框架确立，hitTestBehavior 开放；
- API 12（5.0）：官方交互机制文档系统化，性能体验标准（抛滑 ≤80ms/拖滑 ≤60ms）发布；
- API 18+：嵌套滚动与手势协调接口增强；API 26 起 `onGestureCollectIntercept` 允许自定义干预手势/触摸识别器的收集结果，复杂交叠场景的调控手段更细。
