# 4.2 系统内存压力治理与进程回收

## 系统视角：内存是共享的稀缺资源

4.1 节讲的是应用自己堆里的账。这节换到系统视角：一台设备的物理内存是所有进程共享的，前台应用、后台应用、几十个系统服务都在花。当总量逼近上限，系统必须做选择题——压缩谁、回收谁、杀掉谁。应用如果不理解这套规则，就会出现两类困惑："为什么我的应用退到后台十分钟再回来就重新冷启动了"和"为什么我没干什么，内存占用却一直被系统盯着"。

## 内存压力的分级与通知

系统按内存水位把压力分级，并通过 `onMemoryLevel` 回调通知到应用。应用在 AbilityStage 或 UIAbility 里注册这个回调，收到不同级别时做不同程度的释放：

```typescript
export default class EntryAbility extends UIAbility {
  onMemoryLevel(level: AbilityConstant.MemoryLevel): void {
    if (level === AbilityConstant.MemoryLevel.MEMORY_LEVEL_CRITICAL) {
      // 内存危急：清空图片缓存、释放非必要大对象、关闭次要页面
    } else {
      // 中等压力：收缩缓存上限
    }
  }
}
```

这个回调不是摆设，它是系统和应用的契约：系统在杀进程之前先打招呼，配合释放的应用能显著降低自己被杀的优先级。测试时不用等真实内存耗尽，aa 工具可以直接模拟：

```bash
hdc shell "aa send-memory-level <pid> <level>"   # 向指定进程触发 onMemoryLevel 回调
```

这条命令出自官方 aa 工具文档，联调内存治理逻辑时非常有用。

## 后台进程回收：谁在名单前列

应用退到后台后，进程进入"缓存"状态。系统回收后台进程时按优先级排序，大致规律：

- **有用户可感知行为的进程靠后**：正在播放音乐（申请了长时任务）、导航中的进程，系统尽量保留；
- **纯缓存进程靠前**：退后台又没任何后台任务声明的进程，是回收的首选；
- **内存占用大的进程靠前**：同等优先级下，占内存多的先被牺牲——这就是为什么要控制自家应用的后台驻留内存。

官方后台任务文档把合规的后台存活手段收敛为四类：短时任务（实时性要求高、耗时不长，如保存笔记）、长时任务（后台播放、导航、设备连接等用户可感知场景，可避免进程被挂起）、延迟任务、代理提醒。这套设计的意图很明确：**想在后台活着，就声明自己要干什么，而不是偷偷跑**。

用户侧的清理动作也走这条链：单任务卡片上滑，对应 UIAbility 退出并执行 onDestroy；一键清理批量退出所有任务卡片；PC/2in1 平板上从 Dock 栏退出时 onDestroy 不保证回调（官方应用停止文档原话）——重要状态别只指望在 onDestroy 里保存。

## 内存压缩与其他治理手段

回收之外，系统还有不伤进程性命的手段：

- **内存压缩**：把长时间不活跃的匿名页压缩进 zRAM 分区，腾出物理内存，需要时再解压换回。代价是换回时的解压延迟——后台应用回前台"卡一下"的部分原因就在这里；
- **进程挂起/解冻**：后台进程被冻结（不调度 CPU），回前台再解冻，省 CPU 也省内存换页开销[待验证：鸿蒙应用冻结机制的实现细节与版本范围]；
- **存储与文件页回收**：文件缓存页在压力下直接丢弃，下次读重新进页缓存——这解释了内存紧张时应用切回后读文件变慢的现象。

这些手段对应用透明，但会在 Trace 和响应时延上留下痕迹。分析"回前台慢"问题时，先看进程是否被杀重载（冷启动路径），再看是否经历了压缩换回/解冻。

## 应用侧的配合清单

1. **实现 onMemoryLevel**：按级别分级释放——中等压力收缩缓存，危急压力清空可重建的大对象（图片解码缓存、列表预加载数据）。
2. **后台瘦身**：退后台时在 onBackground 里停动画、注销订阅、释放非必要资源。后台驻留内存越小，被杀顺序越靠后，回来也越快。
3. **用合规的后台任务**：需要后台运行就申请长时任务等正式通道；绕过管控的保活手段在鸿蒙上活不长，还耗电。
4. **别在 onDestroy 赌状态**：用户清理卡片时有回调，Dock 退出不保证。关键状态在 onBackground 或页面切换时就落盘。
5. **缓存设计自带上限**：任何缓存 Map/图片池都要有容量上限和淘汰策略，无界缓存等于替系统内存压力火上浇油。

## 在工具中验证

- `hdc shell "hidumper --mem"` 看全系统内存水位与各进程占用排行；
- `hdc shell "aa send-memory-level"` 验证应用的分级释放逻辑是否真的释放了（前后各抓一次 Snapshot 或 hidumper --mem 对比）；
- 复现"后台被杀"：开一堆应用把内存压上去，观察自家进程是否被回收、回收后回前台走的是什么启动路径（Launch 模板可确认是冷启动还是恢复）。

## 常见问题与误区

**"被杀了就是系统乱杀"。** 先自查三件事：后台驻留内存多大、有没有该申请的后台任务没申请、onMemoryLevel 有没有响应。系统按规则办事，规则对配合者有利。

**"onMemoryLevel 里释放了就万事大吉"。** 释放的是 ArkTS 堆对象还不够——图形 buffer、Native 内存同样计入进程占用。图片密集型应用的治理重点往往在 PixelMap 缓存，而不是 JS 对象。

**内存压力只影响后台。** 内存危急时前台应用同样会收到高级别回调，极端情况前台也会被限制分配甚至触发 OOM。治理是全时段的事。

## 版本演进

- API 9–11：onMemoryLevel 回调与后台任务框架随 Stage 模型提供；
- API 12（5.0）：单框架后后台管控收紧，长时任务等合规通道成为唯一的后台存活手段；
- API 20+（6.0）：资源泄漏检测（句柄、线程、内存）进入官方 DFX 体系；应用预启动（aa pre-start）等能力让"回前台体验"与"内存治理"之间的矛盾有了系统级解法——预先把应用拉到生命周期的某个阶段，用户点开时更快。
