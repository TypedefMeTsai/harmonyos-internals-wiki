# 第 4 章：内存管理

鸿蒙应用的内存问题有两个层面：应用进程内部的堆内存（方舟运行时怎么分配、怎么回收），和系统层面的内存总量（内存不够时谁被压缩、谁被回收）。前者决定应用会不会 OOM、会不会 GC 卡顿；后者决定应用退到后台后能不能活下来、回来时走冷启动还是秒开。

这两个层面经常被混为一谈：用户说"这应用越用越卡"，可能是堆泄漏导致 GC 频繁，也可能是系统内存紧张反复回收它的缓存进程导致每次回来都重载。还有一个常见错觉：托管语言有 GC 就没有内存问题——恰恰相反，泄漏在 ArkTS 里照样高发，只是形态从"忘了释放"变成了"忘了断开引用"。

本章分两节把两层讲清楚。4.1 看进程内部，4.2 看系统全局；两节合起来，才能完整回答"这台设备上我的应用的内存到底被谁花了、被谁收了"。

## 各小节地图

- **4.1 方舟运行时内存模型与 GC**：ArkCompiler 运行时如何组织堆、HPP GC 的分代模型与混合算法、GC Root 与标记-清除的工作方式，以及怎么用 Snapshot 和 Allocation 工具定位泄漏与分配热点。"临时对象便宜、中途存活对象贵"这条工程直觉也在这一节建立。
- **4.2 系统内存压力治理与进程回收**：系统内存水位机制、onMemoryLevel 回调的分级响应、后台进程回收的优先级规则，以及应用该怎么配合治理（后台瘦身、合规后台任务、缓存自带上限）而不是对抗治理。

## 阅读顺序

先 4.1 后 4.2。4.1 是第 21 章内存实践案例的机制基础；4.2 与第 11 章功耗、第 9 章 AppFreeze 都有交叉，读的时候注意"应用该做什么"这条主线。来自 Android 背景的读者可以把 4.2 类比 LMKD 的低内存回收，但鸿蒙的回收更强调后台任务的合规声明，差异在正文里说明。两节都给了可直接执行的验证命令（Snapshot、aa send-memory-level、hidumper --mem），建议边读边在真机上跑一遍。
