# 第 5 章：并发与调度

ArkTS 是单线程语言：UI 和所有业务代码默认跑在同一个主线程的事件循环上。一旦某个函数在主线程跑了 50ms，这 50ms 里事件不分发、帧不渲染——用户看到的就是卡顿，再久一点就是 AppFreeze。把耗时工作挪出主线程，是鸿蒙应用性能的必修课。

但"开个线程"在 ArkTS 里不是一句话的事。ArkTS 选择了 Actor 并发模型：线程之间不共享堆，对象默认序列化传递。这套设计消灭了数据竞争，也把成本摆在了明面上——传什么、怎么传、传多大，都直接影响性能。本章三节分别回答三个问题：用什么并发设施（TaskPool 还是 Worker）、怎么在线程间高效共享数据（Sendable）、系统层面的任务调度是什么样的（FFRT 与异步 I/O）。

## 各小节地图

- **5.1 ArkTS 并发模型：Actor、TaskPool 与 Worker**：为什么 ArkTS 不给共享内存加锁的经典模型；TaskPool 的调度器、优先级队列与扩缩容机制；Worker 常驻线程的定位；两者的官方对比数据与选型规则。
- **5.2 Sendable 共享对象与线程间通信**：Sendable 协议如何让对象在线程间引用传递而不深拷贝，100KB 数据约 1ms 的序列化开销意味着什么，AsyncLock 和 SendableContextManager 解决什么问题。
- **5.3 FFRT、异步 I/O 与系统任务调度**：系统级并发框架 FFRT 的任务与依赖模型；主线程、TaskPool、Worker、FFRT 任务池在整机并发全景中的分工；为什么 ArkTS 的异步 I/O 不占 ArkTS 线程。

## 阅读顺序

5.1 是地基，必读；5.2 在需要跨线程传大对象或共享状态时读；5.3 偏系统机制，做底层性能分析（Trace 里看 I/O 线程、系统任务）时需要。
