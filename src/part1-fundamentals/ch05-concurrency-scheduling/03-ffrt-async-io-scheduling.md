# 5.3 FFRT、异步 I/O 与系统任务调度

## 应用之外的并发世界

5.1、5.2 讲的是应用自己开的并发。但就算应用一行并发代码不写，进程里也在跑一堆系统线程：异步文件 I/O 的工作者、网络栈的回调线程、图片解码的后台任务。这些系统级并发不跑在 ArkTS 线程上，而是跑在一个叫 **FFRT** 的系统并发框架上。理解它，才能看懂 Trace 里那些不属于任何业务线程的泳道，也才能回答"异步 API 到底异步在哪"这类问题。

## FFRT：Function Flow Runtime

FFRT（Function Flow Runtime，OpenHarmony 仓库 `resourceschedule/ffrt`[待验证：仓库路径]）是系统级的并发编程框架。官方概述对它的定位：采用**基于任务的调度**方式，开发者只需关注任务及其依赖关系，无需处理底层线程和计算资源；采用**基于协程的任务执行**方式，提高任务并行度、提升线程利用率，目标是解决系统线程资源滥用问题——如果每个系统服务都自己开线程池，整机线程数会失控，调度开销和内存占用都会浪费。

FFRT 的核心概念：

- **任务（Task）**：执行单元，提交时声明输入依赖、输出依赖和属性；调度器根据依赖关系和 QoS 决定执行时机并选工作线程（`ffrt_submit` 接口语义）。
- **依赖模型**：任务间用数据依赖（而不是手写锁和条件变量）编排执行顺序，构成任务图。
- **三种并发范式**（官方并发范式文档）：**串行队列**（Serial Queue，按提交顺序逐一执行，保证顺序性和共享资源访问安全）、**并发队列**、**图依赖**。
- **协程执行**：任务在工作线程上以协程方式运行，任务内阻塞（等锁、等 I/O）时让出执行栈，线程去跑别的任务——这是"提高线程利用率"的机制所在。
- **QoS 与感知调度**：任务带 QoS 等级，调度器结合负载和核型（大小核）放置任务。

使用约束也值得注意：FFRT 任务调度到哪个线程是**随机的**，任务内禁止依赖线程绑定行为（thread_idx、线程优先级、线程亲和性）；标准库递归互斥锁在 FFRT 任务里可能死锁，要换成 FFRT 提供的递归互斥锁——因为标准库以线程标识记录锁所有者，而 FFRT 的执行栈不等于线程。

## 整机并发全景：主线程、TaskPool、Worker、FFRT

官方《应用并发设计》最佳实践把鸿蒙的并发设施画成了一张分工图，照原文转述：

- **主线程**：执行 UI 业务、不耗时操作、**单次 I/O 任务**；与其他 ArkTS 线程**共享系统 I/O 线程池**，不阻塞当前 ArkTS 线程；
- **TaskPool 高并发任务池**：执行耗时任务，基于 TaskPool 封装任务执行入口，可统计模块负载，开发者不自己开线程；
- **Worker 线程**：执行常驻任务，常驻运行的 CPU 密集型、耗时任务，限制 64 个；
- **FFRT 任务池**：**系统任务**——系统分发到 FFRT 线程的业务，例如异步 I/O 任务，开发者无需关注；用户任务（C/C++ 侧通过 FFRT API 提交的耗时任务），支持负载均衡与线程生命周期管理。

这张图的要点是分工边界：**应用层的并发（TaskPool/Worker）与系统层的并发（FFRT）是两套池子，各管各的**。应用代码碰不到 FFRT 的线程管理，只能通过 C/C++ API 提交任务，或者间接使用——系统 Kit 的异步实现很多跑在 FFRT 上。

## 异步 I/O 为什么不占 ArkTS 线程

看一段最普通的代码：

```typescript
import { fileIo as fs } from '@kit.CoreFileKit';

// 异步读文件：立即返回 Promise，不阻塞主线程
let content = await fs.readText(filePath);
```

`await` 期间主线程在干什么？在跑别的事件——渲染、输入响应照常。真正的磁盘读取发生在**系统 I/O 线程池**（FFRT 管理的线程）里，读完后结果被包装成任务投递回主线程的事件循环，Promise 兑现。这就是"主线程与其他 ArkTS 线程共享系统 I/O 线程池，不阻塞当前 ArkTS 线程"的含义。

对照组是同步 API：

```typescript
let content = fs.readTextSync(filePath);  // 主线程亲自读盘，读完才能干别的
```

主线程执行同步读盘时，Vsync 来了没法响应、触摸事件排队——文件大一点儿就是一帧红帧，再久一点（官方 AppFreeze 的 THREAD_BLOCK 判定时长）就是无响应。所以规则只有一条：**主线程只用异步 I/O；同步 API 留给 TaskPool/Worker 线程内部**。网络请求（@kit.NetworkKit 的 http 模块）同理，本身就是异步设计，回调经事件循环回主线程。

## 在 Trace 中看系统任务

- **异步 I/O 的工作线程**：CPU 会话里能看到不属于 ArkTS 线程的 I/O 工作者泳道，读文件、解压、解码的耗时落在那里。主线程"等待"的区间如果和某个 I/O 线程的活动区间对应，说明逻辑正常——这是异步等待，不是卡死。
- **主线程同步 I/O 的特征**：主线程泳道里出现 fs/数据库相关的长区间，且期间没有渲染活动——直接改异步或挪线程。
- **FFRT 任务的辨识**：系统 Kit 提交的任务在线程名和 Trace tag 上带 ffrt 特征[待验证：各版本 Trace 中 FFRT 线程的命名规则]；遇到"不知道谁在跑"的系统线程，先看线程名再查对应 Kit 的文档。

## 常见问题与误区

**"异步 API 慢，换同步的快"。** 同步 API 省掉的是任务投递的微秒级开销，换来的是主线程停摆。耗时操作没有"同步更快"这一说，只有"放在哪个线程"的区别。

**"系统 I/O 线程池可以配置"。** 应用控制不了它的大小和调度，也不需要控制——这正是 FFRT 存在的意义：系统级任务的线程资源统一治理。应用能控制的是自己提交任务的时机和粒度。

**把 FFRT 当应用的并发工具。** ArkTS 侧开发用 TaskPool/Worker 就够；FFRT 的 C API 面向 Native 层和系统服务开发，混用两套模型（尤其锁语义差异）容易踩坑，官方开发指南里的约束（禁止线程绑定、换用 FFRT 锁）要先读。

## 版本演进

- API 9–11：FFRT 作为系统并发框架服役于系统服务层，应用侧无感；
- API 10：`ffrt_function_kind_t`、任务提交等 C API 对外可见（native kit）；
- API 12（5.0）：官方高性能并发框架说明发布，"主线程共享系统 I/O 线程池"的模型写入最佳实践；libuv 双 loop 机制开始归一（官方 libuv 文档：未来版本逐步把应用模型事件循环归一，解决双 loop 调度问题）[待验证：事件循环归一在当前版本的进展]；
- API 20+（6.0）：并发范式文档（串行队列/并发队列/图依赖）、协程化调度的细节公开，FFRT 对大小核的感知调度成为"软硬芯协同"叙事的一部分。
