# 第 17 章：OpenHarmony 系统优化

## 本章导读

本书前三部分讨论的视角是"应用跑在系统上"：应用侧怎么做、系统侧给了我们什么工具。从这一章开始换一个视角：如果我们本身就是做系统的——做 OpenHarmony 发行版、做行业终端、做开发板产品——性能优化从哪里下手。

两类读者的关心点完全不同。应用开发者面对的是 1100ms 的启动时延红线和 60fps 的滑动帧率；系统开发者面对的是整机的开机时长、镜像大小、内存占用基线，以及几十个系统服务在启动阶段的编排。一个行业平板从按电源键到 Launcher 可交互是 20 秒还是 40 秒，一个安防设备从复位到相机出流是 3 秒还是 8 秒，这些是系统级的性能指标，决定了产品能不能用。

本章只设一节，但这节覆盖三个递进的主题：

**编译构建与镜像裁剪**。OpenHarmony 的构建体系由 GN 描述依赖、Ninja 执行编译、hb 命令封装整套流程。理解 `hb set`、`hb build` 背后发生了什么，才知道裁掉一个部件（part）会少编哪些目标、少打哪些文件进镜像。镜像裁剪不是简单的"删文件"，而是沿着部件依赖图做减法：裁掉一个高层部件，它独占的底层库才能被连带裁掉。

**开机耗时分析**。OpenHarmony 标准系统的启动链路是：Bootloader → 内核 → init → ueventd/watchdog 等基础进程 → appspawn → SAMgr 拉起系统服务 → Foundation → 开机动画 → Launcher。每一段都有对应的观测手段：init 阶段看 dmesg 和 init 日志，系统服务阶段看 SAMgr 的启动日志和 hitrace，开机后期看 bootanimation 退出时间点。我们会讲怎么用 bootevent 参数和 hitrace 把开机过程切成可量化的阶段。

**系统服务按需加载**。OpenHarmony 的系统能力（System Ability，SA）由 SAMgr 统一管理，加载策略写在一个 XML 配置里：哪些随系统启动、哪些按需拉起、哪些压根不进镜像。把"按需"用好，是开机时长和常驻内存双收益的手段。

## 本章与前后文的关系

第 1 章讲过 SAMgr、init 与进程骨架的机制原理，本章是它的实战续篇——机制懂了，这里讲怎么量、怎么裁、怎么改。读完本章后进入第 18 章，讨论系统做好之后，面对不同设备形态时应用侧要面对的差异。

## 适用读者

- OpenHarmony 发行版/行业终端的系统开发者
- 需要把 HarmonyOS 生态经验迁移到 OpenHarmony 设备开发的应用开发者
- 对"应用进程是从哪来"感兴趣、想理解 appspawn 拉活链路的读者
