# 18.1 手机、折叠屏、平板、PC、穿戴与车机

## 为什么设备形态是性能问题

一个在手机上演示得很好的页面，装到平板上滑动掉帧；一个在直板机上秒开的详情页，在折叠屏展开瞬间白屏半秒；一个手机应用原样搬上 PC，窗口被用户拖宽后布局错乱——这些不是"适配没做"的 UI 问题，它们有明确的性能机制：屏幕像素量、窗口尺寸变化事件、能力差异和连续性要求，每一项都会转化成帧耗时、内存和时延。这一节把六种设备形态逐一拆开，讲清楚差异在哪里、影响什么指标、用什么机制应对。

## 六种形态的性能画像

### 手机（直板机）

基准形态。60Hz/120Hz 刷新率、竖屏为主、窗口尺寸基本固定。应用性能的验收口径（启动完成时延 ≤1100ms、点击响应 ≤100ms 等，见《应用性能体验建议》）都是以手机为基准设备定义的。手机上做过的优化结论不能直接外推到大屏：大屏的像素量可能是手机的 2-3 倍，渲染负载完全不同。

### 折叠屏

折叠屏的核心特征是**运行中的窗口尺寸突变**。从折叠态到展开态，屏幕宽度可能从约 300vp 跳到约 600vp 以上（视具体机型），窗口管理器会向应用下发尺寸变化，触发整棵组件树重新布局。如果页面布局耗时本来就贴着 16ms 预算线，展开瞬间的这次全量重排就会丢帧。

折叠状态的感知通过 `display` 模块完成：`display.isFoldable()` 判断是否可折叠设备，`display.getFoldStatus()` 查询当前折叠状态（`FOLD_STATUS_EXPANDED` 展开、`FOLD_STATUS_HALF_FOLDED` 半折叠、`FOLD_STATUS_FOLDED` 折叠），`display.on('foldStatusChange', callback)` 监听状态变化。三折叠设备还有更细的显示模式（`FoldDisplayMode`，如主屏、子屏、双屏协同、全展开等）。

半折叠（悬停）是一个特殊交互形态：设备像笔记本一样半开，上半屏显示内容、下半屏作为交互区。ArkUI 提供了 FolderStack（折叠屏悬停布局容器，API 12+）和 FoldSplitContainer（二分栏/三分栏容器，API 12+）处理这类布局，不需要自己算折痕位置。

### 平板

平板形态的关键是**横屏多窗口**。平板默认横屏使用，且支持自由多窗：应用窗口可能被用户拖成任意宽高比。这意味着不能假设窗口尺寸只有"竖屏"和"横屏"两种，布局必须对连续尺寸变化鲁棒。官方的一多文档把这套能力称为"断点 + 栅格"：按窗口宽度划分断点（如 xs/sm/md/lg），每个断点对应一套栅格系统，布局随断点切换而不是随具体像素值切换。

### HarmonyOS PC

HarmonyOS PC（API 12 起进入产品化）带来三个新约束：

1. **键鼠输入**：没有触摸，hover、右键、滚轮、键盘快捷键成为一等交互。触摸时代的"按住滑动"手势要重新设计。
2. **自由窗口**：窗口可拖拽、可最大化、可并排，尺寸变化比平板更频繁。
3. **性能画像不同**：PC 的 CPU 更强但散热和功耗策略不同，且用户会长时间多任务并行——你的应用可能和十几个窗口同时在前台可见，Vsync 驱动的动画和轮询任务在"可见但非焦点"状态下是否该降频，需要主动设计。

PC 形态在官方的时延规范里与手机、平板并列（适用设备含"PC/2in1"），启动、点击响应等红线同样适用。

### 穿戴（手表）

手表走的是另一个极端：2 英寸左右圆屏或方屏、内存有限、电池极小、交互以抬腕和旋转表冠为主。性能预算全面收紧：动画帧率、图片分辨率、列表长度都要按手表规格重新定。一些 API 在穿戴设备上行为不同或直接不可用——例如 FoldSplitContainer 的参考文档明确标注"在 Wearable 设备上使用时应用程序运行异常"。工程上手表通常独立 device type，甚至独立设计页面，不与手机共用布局。

### 车机

车机是横置大屏 + 严格的安全合规约束。性能上的特殊点：CPU 规格参差不齐、系统常驻服务多、行车模式下交互受限（不允许复杂输入）。车机应用在 module.json5 中用 `car` 设备类型声明，资源目录也可以建 `car` 限定词目录做差异化。

## 一次开发多端部署：布局自适应的三件套

官方"一多"体系给的是三层工具，按抽象级别从低到高：

**断点（Breakpoint）**：以窗口宽度（不是屏幕宽度）划分区间，典型分法是 xs / sm / md / lg / xl。窗口尺寸变化时先判断落在哪个断点，再决定布局形态。用窗口宽度而非屏幕宽度，是因为自由多窗下应用窗口只是屏幕的一部分。

**栅格（Grid）**：每个断点对应一套栅格参数（列数、间距、边距），组件按占据的列数描述尺寸。断点切换时组件跨列数变化，布局随之重排。

**典型布局模式**：一多文档总结了若干可直接套用的模式——单栏/双栏切换、导航栏从底部 Tab 变为侧边栏、列表在大屏变为宫格、详情页在宽屏变为左右分栏（FoldSplitContainer 正是折叠屏/大屏分栏的现成实现）。多行聚类布局这类模式则针对阔折叠"屏幕变矮"的场景，把纵向排布改为横向，把显示空间让给有效内容。

[图：同一页面在手机（单栏）、折叠展开态（双栏）、平板横屏（三栏）下的布局切换]

性能视角下要提醒一句：**布局模式切换是有成本的**。断点变化引发的整树重建和 Scroll 嵌套 List 重建是同一类开销。宽屏双栏用两个并列的 LazyForEach 列表实现时，确认每个列表都设置了明确宽高或 `layoutWeight`——无边界约束下 LazyForEach 的视口裁剪会失效，瞬时实例化全部数据项，首帧渲染耗时会指数级恶化（见《LazyForEach 性能优化》最佳实践）。

## 能力差异化：SysCap 与 canIUse

"一多"的另一半是能力侧。不同设备开放的系统能力不同，用 SysCap（System Capability）描述。规则是：

- 应用工程的 device type 配置多个设备类型时，工程的**要求能力集**默认取这些设备支持能力集的**交集**，**联想能力集**取**并集**。
- 只有当应用要求能力集是设备支持能力集的子集时，应用才能在该设备上分发、安装和运行。
- 交集之外、并集之内的 API——也就是"部分设备有、部分设备没有"的能力——调用前必须用 `canIUse("SystemCapability.XXX.XXX")` 做运行时判断，不可用分支要有降级逻辑。

```typescript
import { canIUse } from '@kit.AbilityKit';

if (canIUse('SystemCapability.Multimedia.Camera.Core')) {
  // 相机相关逻辑
} else {
  // 无相机设备的降级界面
}
```

单设备工程不需要 `canIUse`，直接查接口能力即可；多设备工程里漏掉 `canIUse` 的后果是：在没有该能力的设备上调用，接口未定义异常或运行异常。

## 折叠屏展开/折叠连续性

连续性有官方验收标准（《折叠屏 UX 设计指南》开合连续性 4.1.1）：应用在折叠/展开后不应出现体验下降——不能跳到别的页面、滚动位置不能偏移、输入内容不能丢失、图片不能模糊、播放进度不能变化。

从机制上看，展开/折叠触发的是一次窗口尺寸变化 + Configuration 变化。保证连续性要做四件事：

1. **状态存活**。页面级状态（滚动位置、输入框内容、播放进度）要挂在能跨重建存活的载体上：`@StorageLink`/`AppStorage`、ViewModel 单例，或者对应组件的 `Scroller` 对象。如果状态只存在于被销毁重建的局部组件里，展开折叠就丢。
2. **监听并响应尺寸变化**。用 `display.on('foldStatusChange')` 或在组件上用 `onAreaChange` 感知变化，在回调里只调整布局参数，不重新拉数据、不重建播放器。相机这类对形态敏感的模块例外：折叠状态变化时要重新查询可用相机并决定是否重新配流（半折叠态与展开态支持的相机可能不同，官方相机文档建议：若前后状态支持的相机一致则不必重新配流，避免无谓的初始化耗时）。
3. **布局使用自适应描述**。用断点/栅格/RelativeContainer 描述布局，让框架在尺寸变化时自己算出正确结果，而不是在代码里写死像素值。
4. **验证方式**。真机上做"折叠-展开-半折叠"循环操作，同时用 Frame 会话录制：尺寸变化那一帧是否出现 AppDeadlineMissed；变化前后滚动偏移、输入内容、播放进度是否保持。折叠连续性的丢帧通常是布局重建超时，优化手段与第 20 章布局优化相同——减节点数、固定宽高建布局边界、LazyForEach 配复用。

## 迁移检查清单

把一个手机应用推向折叠屏/平板/PC 时，按顺序检查：

- [ ] device type 声明是否覆盖目标设备；交集外 API 是否都有 `canIUse` 保护
- [ ] 布局是否基于断点/栅格，有没有写死宽度
- [ ] 大图、大列表在大分辨率下的内存与渲染耗时是否实测过（不要外推手机数据）
- [ ] 窗口尺寸连续变化（拖拽缩放、折叠展开）时是否丢帧
- [ ] 滚动位置、输入内容、播放进度在形态切换后是否保持
- [ ] 手表/车机等极端形态是否走了独立设计而不是"凑合跑"
