# 第 18 章：设备形态与差异

## 本章导读

HarmonyOS 从一开始就把自己定位成"全场景"系统：同一套 ArkTS 代码，要跑在 6 英寸直板手机上、8 英寸展开的折叠屏上、13 英寸平板上、带键盘的 HarmonyOS PC 上、2 英寸的手表上，以及车机的横置大屏上。"一次开发，多端部署"是官方给出的答案，但这六个字容易让人误以为"写一遍代码到处跑"——真实的含义是：**工程写一次，但每一种设备形态的能力差异和交互差异，都需要你显式地设计和验证**。

对性能工程师来说，设备形态差异不是 UI 适配问题，而是性能问题的来源清单：

- **屏幕变大，像素变多**。折叠屏展开态、平板、PC 的分辨率远高于手机，同样一张布局树，Measure/Layout/Render 的对象更多，单帧渲染的像素量更大。手机上流畅的页面搬到大屏就丢帧，是常见的迁移事故。
- **窗口会变形**。折叠屏展开/折叠、PC 和自由多窗平板上的窗口拖拽缩放，意味着应用的窗口尺寸在运行时会变。每一次尺寸变化都是一次完整的重新布局，处理不好就是一次肉眼可见的卡顿。
- **能力不齐**。手表没有相机、车机没有某些传感器、PC 的输入是键鼠而非触摸。调用了设备不支持的系统能力（System Capability，SysCap），轻则功能失效，重则无法安装。
- **连续性要求**。折叠屏从折叠到展开，用户期望页面滚动位置不变、输入内容不丢、视频播放进度不断。这是体验验收标准，不是锦上添花。

本章用一节覆盖这些主题：六种主流设备形态的硬件与系统差异如何影响应用性能，一次开发多端部署的自适应布局体系（断点、栅格、典型布局模式），用 SysCap 和 `canIUse` 做能力差异化，以及折叠屏展开/折叠连续性的实现要点。

读完这一章，你应该能回答：同一个 HAP 装上折叠屏和平板后，为什么一个流畅一个卡；以及当产品经理说"这个页面要上 PC"时，你要检查哪些东西。

## 与其他部分的关系

本章是一座桥：第 17 章讲的是"系统怎么造"，本章讲的是"应用跑在什么形态的 system 上"，而第 19 章开始的第五部分讲的每一项应用优化（启动、渲染、内存、功耗），在不同设备形态上都要重新验证一遍——手机上成立的结论，展开态的折叠屏上未必成立。建议读完本章后，把第五部分每一节的验证方法在至少两种形态的设备上各跑一遍。
