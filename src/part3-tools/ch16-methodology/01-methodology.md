# 16.1 性能问题的定义、证据与修复验证

## 为什么需要方法论

回顾前面章节的案例，会发现它们的骨架完全一样：第 7.2 节先框选 2.5 秒区段确认"丢 16 帧、丢帧率 7%"，再定界 App 侧，再深入到 BuildLazyItem；第 8.2 节先体检确认完成时延超 900ms，再钉起止点，再分泳道归因；第 9.2 节先看 Reason 字段确定故障类型，再按类型选择日志读法。问题各不相同，动作却高度同构——**先定量，再定界，后定位，最后验证**。

把这个同构的动作显式化，就是方法论。它的价值不在第一次分析（那时热情最高、最不缺时间），而在第一百次：疲惫、催进度、现象模糊的时候，流程能防止我们抄近路掉进坑里。本节给四步框架，然后讨论证据的边界，最后给报告模板。

## 第一步：现象定义

九成的低效排查源于现象没定义清楚。"应用有点卡"不是现象定义，是情绪。合格的定义包含四个要素：

**可测量的指标**：卡是丢帧率、响应时延、完成时延、启动耗时、内存曲线斜率、还是电量百分比？选一个主指标。指标必须来自官方度量体系（Frame 泳道统计、录屏时延、hidumper 数值、SP_daemon 采样），而不是体感描述。

**数值与基线**：当前值多少，期望值多少。官方红线是最现成的基线（响应 ≤100ms、完成 ≤900ms、滑动卡顿率 0ms/s），没有红线的场景就自己定（启动从 1.8s 恶化到 2.6s，基线就是上个版本的 1.8s）。"比基线差多少"决定问题的优先级，也决定修复的验收标准。

**复现条件**：设备型号、系统版本、应用版本、前置状态（冷启动还是热启动、第几次操作）、操作序列。"越滑越卡"和"第一次滑就卡"指向完全不同的根因，第 7.2 节案例里"1000 条数据、逐渐卡顿"这个描述本身就排除了半数假设。

**范围边界**：必现还是偶发？单机还是全机型？某个版本之后才有？范围每收窄一分，假设空间就小一半。线上问题先按设备、系统版本、应用版本三个维度分桶，看问题集中在哪个桶。

## 第二步：证据边界

动手抓数据之前，先想清楚每种证据能证明什么、不能证明什么。四类主要证据形态：

**Trace（hitrace / Profiler 会话）**：能证明"时间花在哪个环节"——线程在 Running 还是等待、哪个函数耗时、帧在哪一侧超时。不能证明"为什么这样写"——Trace 显示 BuildLazyItem 耗时 10ms，它不解释代码为什么没开复用，那是读代码的事。也不能直接证明线上行为的代表性——开发机上抓的 Trace 来自特定设备、特定场景，把一次录制当成普遍事实之前，先确认它能稳定复现。

**日志（hilog / FaultLog）**：能证明"事件发生的顺序与状态"——故障类型、调用栈、队列内容、对端通信。它的局限是采样偏差：日志只记录被打印的东西，没打点的路径在日志里是沉默的，沉默不等于没发生。还有截断风险：超限丢日志（第 15.1 节）、堆栈抓取失败（第 9.2 节的 errno(2)）、瞬时栈抓错栈顶（增强日志存在的理由）。读日志的第一反应应该是"这份记录完整吗"。

**Profiling（采样 / Snapshot / Allocation）**：能证明统计意义上的热点与对象分布。它的局限是自身开销会扰动被测对象——Allocation 录制时应用明显变慢，CPU 高频采样会改变调度行为。Profiling 数据用来定位，不用来度量指标；指标测量要用低开销手段（SP_daemon、aa -W、录屏）。

**复现条件**：最被低估的证据。"只在 120Hz 机型出现""只在内存 8GB 以下设备出现""杀进程后首次启动必现"——每条稳定的复现边界都是一条强约束，能直接否掉一批假设。反过来，偶发问题在提高复现率之前不要急着抓数据，先把"偶发"变"必现"：加压、降配、循环操作、对比开关。

证据使用的总原则：**让证据先于假设存在**。先有了"2.5 秒丢 16 帧"的统计，"列表项创建太贵"才是待验证的假设；没有这个统计，它只是一个猜。

## 第三步：假设与验证

有了现象定义和初步证据，接下来是假设驱动的循环：

1. **列假设**：根据证据列出所有能解释现象的候选根因，写全，包括自己不喜欢的那个（"我上周提交的代码"）。
2. **找判别实验**：对每个假设问同一个问题——如果它是对的，我应该在哪里看到什么？假设"主线程被抢占"，判别证据是 CPU 泳道上主线程的 Runnable 段和抢占者身份；假设"等锁"，判别证据是两次采样栈停在同一个锁上。找不到判别证据的假设，设计上就有问题。
3. **一次只验证一个**：改一个变量，测一次。同时改三处然后指标好转，不知道是哪处起效；指标没动，也不知道是三处都没用还是两正一负相互抵消。
4. **用数据宣布结果**：假设被证实或被否证，都以数值为准。被否证的假设划掉，回到第 1 步——被否证的假设也是成果，它永久缩小了搜索空间。

定界是这个循环里杠杆最大的动作，本书反复出现：丢帧先分 App/RS 两侧（7.1），内存先分 JS 堆/native/图形三层（10.1），时延先分五个环节（8.1），AppFreeze 先分阻塞/繁忙/IPC 三形态（9.2）。每次定界都把假设空间砍掉一半以上，比任何深入分析都快。养成习惯：任何性能问题，先问"它在哪个二分树上"。

## 第四步：修复与回归

**修复**：针对证实的根因选方案。优先级参考官方最佳实践的成熟度——组件复用、懒加载、布局扁平化这类有官方案例和量化数据背书（复用后丢帧率 3.7%→0%）的手段优先，自创的技巧放后面。

**验证**：和修复同样重要，且必须用与现象定义阶段**相同的指标、相同的场景、相同的工具参数**重新测量。优化前 2.5 秒丢 16 帧，优化后就再框 2.5 秒数一次；体检报告原来五项超标，就再体检一次。指标没动，回第三步；指标动了但没达标，继续迭代。感觉层面的"好像快了"不作为验收依据——安慰剂效应在性能领域同样存在。

**回归**：性能修复容易按下葫芦浮起瓢——开组件复用增加了内存占用，预加载换时延增加了功耗。验收时把关联指标一起测：帧率、内存、功耗至少各看一眼。有自动化条件的，把指标写进持续集成（aa -W 测启动、SP_daemon 测帧率电量），让每个版本都有数据，劣化在合入前暴露。

## 调查报告模板

把一次调查写成可复查的报告，是方法论的最后一块。复查的意思是：三个月后的自己、或者从没接触过这个问题的同事，只看报告就能重走整个推理并认同结论。模板如下：

```text
# 性能调查报告：{一句话标题，含指标与数值}

## 现象
- 指标与当前值 / 基线值：
- 设备、系统版本、应用版本：
- 复现条件与操作序列：
- 影响范围（机型/版本/用户量分布）：

## 证据
- 证据 1：{类型：Trace/日志/Profiling/复现边界}
  - 采集方式（工具、参数、区段）：
  - 关键内容：{截图或引用，标注泳道名/字段名}
  - 它证明了什么 / 不能证明什么：
- 证据 2：……

## 分析过程
- 假设列表与逐一验证结果（含被否证的假设及否证依据）：
- 定界过程：{在哪个二分树上走到了哪一层}

## 根因
- 一句话根因：
- 证据链：{从现象到根因的完整推理，每步有证据支撑}

## 修复
- 方案与改动点：
- 替代方案及取舍理由：

## 验证
- 优化前 / 优化后指标对比（同场景同参数）：
- 关联指标回归结果（内存/功耗/其他）：
- 遗留问题与后续跟踪：
```

两个使用要点：一是"被否证的假设"必须写，它们是报告里最省后来人时间的部分；二是关键数据附原始文件指针（Trace 文件名、日志路径、 Profiler 会话导出），截图会过期，原始数据永不过期。

## 结尾：纪律比天赋可靠

性能分析看起来像一门依赖直觉的手艺，实际做起来是一门依赖记录的学问。定义清楚再动手、证据先行、一次一个变量、用数据验收、写下来——五条纪律执行到位，大部分性能问题的收敛速度会快得让自己意外。工具部分（第 13~15 章）给了我们观察系统的眼睛，这一章的纪律决定我们用眼睛看到的东西能不能变成结论。
