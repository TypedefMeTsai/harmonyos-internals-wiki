# 23.1 应用功耗治理实战

## 功耗的账：谁在耗电

应用功耗可以粗分为四笔：屏幕（常亮、高亮度、高刷）、CPU/GPU 计算（渲染、动画、数据处理）、射频（网络请求、定位）、外设（传感器、音频、相机、蓝牙）。应用能控制的主要是后三笔。治理路径也按这个分：后台合规是底线（不合规直接被系统管控+体检打回），前台场景化是进阶（同样的功能用更省的方式实现），帧率与动画是日常大头（贯穿所有前台使用时长）。

## 后台任务合规：硬规则清单

系统的后台管控是硬性的：不做处理的应用退到后台会被挂起或终止进程。官方《后台硬件/软件资源规范》与 AppAnalyzer 体检规则给出了明确红线，逐条翻译：

**CPU 负载**：

- 短时任务：后台进程任务期间 CPU 负载不得高于 8%（8 核负载口径，即总负载 64%）。
- 长时任务：后台进程持续 10 分钟 CPU 使用率不得高于 80%。

**退后台后的资源禁令**（无长时任务的应用）：

- 不允许蓝牙扫描；
- 禁止使用麦克风或扬声器；
- 禁止使用传感器；
- 不得直接或间接持有阻止系统休眠的锁（对应资源必须释放）。

**任务类型匹配**：后台任务必须按原定用途使用（用途要在应用市场功能介绍中声明）、用户可主动开始停止、执行期间用户可感知。耗时不长的后台操作用短时任务，完成后及时取消——短时任务超时或超负载会被系统处置。

**定位/音频的专门要求**：申请定位长时任务的应用，导航时须设置正确的应用场景；音乐类应用须设置正确的音频类型——系统按场景类型做功耗调度，标错类型等于放弃系统的省电优化。

**怎么做**：核对应用申请的每个后台任务类型是否必要；退后台回调（onBackground）里释放传感器、停止扫描、注销 displaySync、停动画；短时任务完成立即 cancel。

**怎么验证**：AppAnalyzer 场景化体检的功耗/后台规则项（规则清单见《AppAnalyzer 全部体检规则》）；后台挂起后用 hidumper、功耗工具看 CPU 与持锁情况。

## 前台场景化建议：官方低功耗规则

《应用功耗体验建议》最佳实践按场景给了前台规则，高频的几条：

- **视频播放场景使用硬件编解码器**；视频弹幕场景走硬件加速。软解 1080p 视频的 CPU 占用和发热远超硬解，这一条不达标基本告别"视频应用"品类。
- **应用处于前台/后台不可见时，动效不使用资源、及时停止**。页面不可见（被覆盖、切 Tab、退后台）仍在跑的动画是纯浪费——20.2 讲的弹幕 displaySync 空刷案例就属于这条。
- **小区域动效、微动效建议帧率 30Hz 及以下**；插画动效、固定源帧率动效跟随内容源。不是每个动画都值得 120Hz。

## 定位、传感器与音频：三个高耗电场景的专门打法

**定位**：持续定位是射频+GPS 的双重开销。能不用持续定位就不用——签到类场景用单次定位；轨迹类场景按精度需求选模式，导航外降采样率；退后台需要定位时必须申请定位长时任务并设置正确场景类型，系统按场景调度功耗策略。无长时任务退后台后继续持定位是体检明确禁止的行为。

**传感器**：监听不注销是传感器功耗的主要来源。页面 onHide/onBackground 时注销监听，回到前台再注册；步数、环境光这类低频数据用系统提供的批处理/低功耗通道而不是高频率订阅。规则层面：无长时任务的应用退后台禁止使用传感器。

**音频**：音乐类应用必须设置正确的音频流类型——系统按类型决定音效链路、混音策略和功耗调度，类型标错（比如音乐标成通知音）会走更高功耗的通路且打断行为异常。后台播放走音频长时任务，停止播放即结束任务。无长时任务退后台使用麦克风或扬声器是体检红线。

## Vsync 降帧与动画功耗

动画和自绘制内容的功耗模型很简单：每一帧都要 CPU 提交 + GPU 绘制 + 显示，帧率翻倍功耗近似翻倍。所以降帧是最直接的功耗手段：

- 属性动画/显式动画用 `expectedFrameRateRange` 声明期望帧率（如装饰动画 expected: 30）。
- 自绘制 UI 用 displaySync 管理帧节奏，不需要刷新时注销对象——官方功耗最佳实践专门警告：displaySync 对象要自己管好生命周期，绘制内容在屏幕外或不再需要时必须注销，避免应用进程空刷帧。
- 静态页面零动画：确认页面静止时没有残留的动画驱动 Vsync 请求。静止页面还在每帧提交的，Frame 会话里一眼可见（Vsync 周期内持续有渲染任务）。

**怎么验证**：Frame 会话的 Display Vsync 与 DisplaySync_cb 子泳道看实际帧率；静止页面观察是否仍有帧任务；功耗工具对比降帧前后的电量消耗曲线。

## 发热与卡顿：互相放大的死循环

发热不是独立问题，它和卡顿互相放大：CPU/GPU 持续高负载 → 温度上升 → 温控策略降频 → 同一代码路径的单帧耗时变长 → 丢帧增加 → 用户感知卡顿。所以"刷着刷着变卡、手机发烫"类投诉，根因往往不是调度问题，而是功耗问题。

反过来，20.2 讲的高阶视效有直接的功耗含义：模糊与自渲染图层交叠导致 HWC 失效、RS 改用 GPU 合成，GPU 负载上升带来发热——发热降频后 GPU 更慢，丢帧更严重。视频应用"看久了又烫又卡"，先查 HWC 是不是失效了。同理，列表滑动里的实时模糊、每帧重算的动画，都是在给这个循环添柴。

治理顺序：先把帧耗时优化到位（第 20 章），再看帧率是否可降（本节），再看合成路径是否高效（HWC），最后才轮到温控层面——前三步做完，多数发热投诉已经消失。

## 功耗分析的工具链

官方功耗最佳实践给出的流程是检测 → 分析 → 优化的循环：AppAnalyzer 体检出规则违规项，功耗类工具（Profiler 的能耗相关数据、DevEco Testing 功耗测试）定位耗电热点，把功耗数据与卡顿、帧率、CPU/内存/网络占用关联分析，改完回归。功耗优化的目标不是"功耗最小"，而是官方那句话：在保障核心功能体验流畅的前提下，降低无效能量消耗。

## 功耗问题的自查顺序

拿到一条"耗电快"的反馈，按这个顺序缩小范围：

1. **先分前台后台**。后台耗电异常 → 查后台任务合规（CPU 负载、持锁、传感器）；前台耗电异常 → 继续往下。
2. **前台看帧**。静止界面是否仍有渲染任务，动画帧率是否虚高，displaySync 是否泄漏。
3. **看合成路径**。视频/自渲染场景查 HWC 是否失效。
4. **看外设**。定位、传感器、音频的场景类型是否正确，退后台是否释放。
5. **最后看网络**。轮询间隔、无效请求、弱网重试风暴——射频是隐藏的耗电大户。

每一步都有对应的验证工具，别跳步：没确认后台合规就谈动画降帧，多半是在错误的战场上使劲。
