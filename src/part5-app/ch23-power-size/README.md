# 第 23 章：功耗与包体积优化

## 本章导读

功耗和包体积是两类"用户不直接说、但会用脚投票"的指标。用户不会投诉"你的应用 GPU 合成占比过高"，他会说"这个应用刷半小时手机就烫"；不会投诉"你的 HAP 里有三份重复的 so"，他会在看到 200MB 下载体积时点取消。

**23.1 应用功耗治理实战**从官方体检规则出发：后台任务合规（CPU 负载红线、退后台资源释放）、前台资源场景化建议（定位、传感器、音频、视频）、Vsync 降帧与动画功耗、以及发热与卡顿的互相放大关系。官方的低功耗规则大多可直接用 AppAnalyzer 体检验证，这一节把规则翻译成"为什么 + 怎么做 + 怎么验证"。

**23.2 HAP 包体积治理**处理另一个工程问题：包是怎么胖起来的。资源冗余、so 多架构重复、ohpm 依赖链雪球、多 HAP 场景下 HAR 的多份拷贝，每一项都有对应的工具：资源精简、deduplicateSo、ohpm list 依赖分析、混淆压缩、HSP/HAR 分包选型。

这两节有个共同的立场：功耗和包体积的优化都要先做测量、列预算、找大头，没有"我感觉"的位置。功耗用 AppAnalyzer 体检与功耗工具链量化，包体积直接解包 HAP 按目录算体积——两件事都是半天能做完的，做完再决定优化哪。

## 与前面章节的关系
功耗不是独立战场：23.1 会大量引用第 20 章的结论——动画帧率、高阶视效、HWC 失效在"流畅性"语境下是丢帧问题，在功耗语境下是发热问题，同一段代码两个视角。包体积则和第 19 章形成张力：HSP 分包能减体积但增加启动 I/O，23.2 会给出这对矛盾的决策规则。读完本章再回头看第 19、20 章，你会发现性能优化从来不是单指标的事。

## 适用读者

- 被用户投诉"耗电快、手机烫"，需要把模糊投诉转化为可验证项的应用开发者
- 负责发版包体积指标、需要给每个版本的增长找原因的技术负责人
- 准备上架、需要过一遍 AppAnalyzer 体检规则的团队
