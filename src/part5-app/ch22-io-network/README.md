# 第 22 章：I/O 与网络优化

## 本章导读

I/O 和网络是两个"不在 Trace 里就很难被发现"的性能黑洞。主线程上一行看似无害的 `fs.readSync`，在文件大或者存储繁忙时就是几十毫秒的帧超时；一个每次冷启动都串行发出的网络请求，就是把 19 章省下来的几百毫秒又还了回去。

第 6 章讲过 Preferences、KV Store 与关系型数据库的机制，第 12 章讲过网络栈。本章落到应用实践，分两节：

**22.1 文件、数据库与序列化优化**。文件 I/O 的规矩（为什么主线程禁令是硬性的、批量读写怎么省系统调用）、Preferences 与 RDB 的选型决策（全量加载内存的键值存储 vs 有连接池的关系型数据库，各自的性能拐点在哪）、跨线程数据传递的序列化开销（为什么 100KB 以上的对象该用 Sendable 引用传递）。

**22.2 请求、缓存与弱网策略**。RCP（Remote Communication Platform）的会话与连接复用、HTTP 缓存（RFC 9111 标准缓存与缓存拦截器）、请求并发控制、弱网环境下的降级与预取策略。

这两节的共同原则是：I/O 与网络的耗时无法消除，只能**挪走**（移出关键路径）、**合并**（批量化）和**消除**（缓存命中）。每条建议都会落到"用什么工具看什么指标"：文件 I/O 看主线程 Trace 里的读写耗时，数据库看查询耗时与连接行为，网络看 Profiler Network 泳道的请求瀑布。

## 为什么这两件事放在一起

I/O 和网络常被分到不同章节，但它们共享同一个故障模式：**阻塞调用出现在不该阻塞的地方**。主线程同步读文件和主线程串行等网络，在 Frame 泳道里呈现完全相同的形态——一段没有渲染产出的空白。排查方法也同构：先确认阻塞段的位置，再判断这段 I/O 是"必须同步"还是"可以异步/预取/缓存"。把两者放在一起，是为了让这套判断变成肌肉记忆：看到主线程空白段，先问它背后有没有文件、数据库或网络。
