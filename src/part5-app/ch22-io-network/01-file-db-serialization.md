# 22.1 文件、数据库与序列化优化

## 文件 I/O：主线程禁令与批量化

**为什么主线程不能碰同步文件 I/O**：闪存读写的延迟不可控——空闲时几百微秒，存储繁忙或遇到垃圾回收时几十毫秒都正常。主线程上一行 `readSync`，赶上坏时机就是一帧甚至几帧的预算。这不是理论风险，AppAnalyzer 体检明确检测"高耗时非 UI 操作"，THREAD_BLOCK 类 AppFreeze 的常见根因之一就是主线程同步 I/O。

**怎么做**：

- 文件读写全部走异步 API（`fs.read`/`fs.write` 的 Promise 形式）或放进 TaskPool。
- 小文件高频读写合并：攒一批写一次。一次 write 系统调用的固定开销（打开、寻址、落盘策略）远大于多写几百字节的边际开销，循环里逐条写文件是最差的形态。
- 大文件分片读写并配合进度反馈，避免一次性分配大 buffer。
- 写入后不立刻需要的数据，别 fsync 成瘾——每次强制落盘都是毫秒级开销，按数据重要性分级。

**怎么验证**：Frame/Launch 会话主线程 Trace 中搜文件操作相关耗时；AppAnalyzer 高耗时函数报告；复现"存储繁忙"场景（后台跑大文件拷贝）再测一遍关键路径。

还有一个容易漏的隐性 I/O：资源与图片加载。从沙箱读一张大图、解码一个字体文件，本质都是文件 I/O，只是藏在框架 API 后面。主线程 Image 加载本地大图、build 里 new 一个读文件的解析器，都是同一个禁令的适用范围。排查时如果主线程耗时段里看不到显式的 fs 调用，往图片解码和资源加载方向查。

## Preferences vs RDB：选型看数据形态

两个存储的性能画像完全不同，选错了怎么优化都别扭。

一个前置提醒：Preferences 和 RDB 的读写 API 都同时提供同步（xxxSync）与异步形式，同步形式的禁令与文件 I/O 相同——不在主线程调用。Preferences 的 get 命中内存所以同步调用通常很快，但首次打开（getPreferences）的加载解析是磁盘 I/O；RDB 的查询走 SQLite 层，慢查询在主线程就是帧超时。冷启动路径上要用 Preferences 读配置，应提前在子线程完成打开并把结果缓存到内存对象。

**Preferences**：轻量键值存储，默认 XML 存储模式，**数据以文本形式保存，应用使用时全量加载到内存**。这决定了它的性能特征：读内存中的键值是纳秒级，但——

- 首次打开要全量加载解析，文件越大打开越慢；
- 全量驻留内存，存大对象（长字符串、base64 图片）就是常驻内存浪费；
- XML 模式不支持多进程并发，多进程场景要用 GSKV 存储模式。

适合：配置项、开关、用户偏好这类"总量小（建议 KB 级）、读多写少"的数据。写操作注意 flush 时机，频繁 flush 同样触发落盘开销。

**RDB（关系型数据库）**：系统默认 WAL（Write Ahead Log）模式、FULL 落盘方式，默认 4 个读连接和 1 个写连接。性能特征：

- 读操作可以并发（4 读连接池），写操作全局串行（同一时间一个写，并发写串行执行）；
- 查询走索引，数据量大时远优于全量扫描的键值遍历；
- 有建库、建表、解析的固定开销，小数据量场景不如 Preferences 直接。

适合：结构化、有查询条件、数据量大的业务数据（消息记录、订单、内容列表）。

选型决策表：

| 数据特征 | 选择 |
| --- | --- |
| 几十个配置键值 | Preferences |
| 需要条件查询、排序、分页 | RDB |
| 单条数据大（富文本、媒体元数据） | RDB（或文件 + RDB 索引） |
| 多进程读写 | Preferences 的 GSKV 模式，或 RDB |
| 高频小写入（埋点、日志类） | 内存缓冲 + 批量写，慎选直接落库 |

RDB 的性能实操：查询必须走索引（用 `relationalStore.getQuerySqlInfo` 拿到实际执行的 SQL 检查）；批量写用事务包裹（事务内多次写只付一次 WAL 同步成本）；`.db-wal` 文件是 WAL 日志，不手动删。还要注意结果集的生命周期：ResultSet 用完要 close，长事务会挡住 WAL 的检查点回收，间接拖慢后续写操作。

**怎么验证**：打开和查询分别用 HiTraceMeter 打点，冷启动场景在 Launch 会话里看存储相关耗时是否落在首帧前；大查询用 getQuerySqlInfo 确认索引命中；批量写对比事务内外的总耗时。

## 序列化：跨线程传递的隐藏开销

往 TaskPool/Worker 发任务时，参数默认走 Structured Clone 式的序列化拷贝。对象小无所谓，对象一大（官方《本地文件与数据多线程 I/O》最佳实践给出的分界是 100KB 以上）序列化本身就成为瓶颈：拷贝耗时、双倍内存、GC 压力，且数据库查询结果集这类带方法的对象根本没法直接拷。

**Sendable 的解法**：@Sendable 装饰的类实例以共享内存形式在并发实例间传递，用引用代替拷贝。两个适用场景（官方文档原文）：跨并发实例传输大数据（100KB 以上）；跨并发实例传递带方法的 class 实例对象。文件 I/O 多线程处理的标准姿势是：定义 Sendable 对象存放写入数据，封装 TaskPool 函数传入引用，子线程直接读写同一份数据。

系统也给了配套能力：`@kit.ArkData` 提供 SendableRelationalStore，可以从 RDB 查询结果集直接获取 Sendable 类型的 ValuesBucket 用于跨线程传递；SendablePreferences 同理。数据库结果要交给子线程处理时，走 Sendable 通道而不是先转 JSON。

**怎么验证**：HiTraceMeter 打点测"任务参数准备 → execute 调用返回"的耗时，对比序列化传递与 Sendable 传递的差异；大对象场景对比内存峰值。

一个边界要说清：Sendable 解决的是"传递成本"，不是"访问成本"。多个并发实例持有同一 Sendable 对象的引用后，并发写需要靠 Sendable 自身的线程安全语义（如 @Sendable 类的异步锁机制）保护，把 Sendable 当普通对象随意并发读写会引入另一类正确性问题。大数据只读共享（子线程消费、主线程产出后不再改）是它最干净的用法。

## 举一反三：I/O 问题的通用排查

主线程出现不明帧超时，而 ArkTS 调用栈显示停留在业务代码时，问三个问题：这行代码背后有没有文件 I/O（包括图片解码、资源加载这些隐性 I/O）？有没有数据库查询？有没有跨进程/跨线程的序列化？三个方向分别对应本节的三个主题，工具分别是 Frame 会话主线程 Trace、getQuerySqlInfo + 查询打点、HiTraceMeter 自定义打点。
