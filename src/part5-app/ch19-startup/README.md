# 第 19 章：启动优化

## 本章导读

冷启动是用户对一个应用的第一印象，也是官方体验规范里写得最死的指标：《应用性能体验建议》规定**应用启动加载完成时延应 ≤1100ms，元服务应 ≤340ms**（适用设备：手机、平板、PC/2in1、智慧屏、车机、手表）。这不是建议，是类型为"规则"的条款，开发自测用 DevEco Studio AppAnalyzer，上架还有 AppGallery Connect 云测试性能检测兜着。

但"1100ms"这四个字有个陷阱：它的口径是从用户点击图标到启动过程动画/视频结束，而真正决定用户感受的，是中间每一个阶段各花了多少时间、钱花在了谁身上。一个 900ms 达标的启动，可能 500ms 在等网络返回，也可能 400ms 在加载根本用不到的模块——两种达标的含金量完全不同，前者网络一抖就破线，后者是结构性浪费。

本章分两节：

**19.1 冷启动链路与阶段拆解**。先建立共同语言：冷启动、温启动、热启动的区别；从点击图标到首帧上屏的完整链路——Launcher 响应点击、appspawn 拉进程、AbilityStage/UIAbility 生命周期、首页组件构建、首帧送显；以及 DevEco Profiler Launch 会话把这条链路切成七个可量化阶段的方式和每个阶段对应的 Trace 点。读完这一节，给你一个启动慢的应用，你能说出慢在哪一段。

**19.2 启动优化实战清单**。把官方最佳实践里的优化手段整理成可直接执行的清单：生命周期回调里的耗时操作异步化、延迟初始化与 AppStartup 启动框架、lazy import 与动态 import、import 路径展开与 HAR 导出拆分、网络请求提前与首帧数据预取、startWindowIcon 规格、单 HAP 场景的 HAR/HSP 选型。每条给出"为什么有效 + 怎么做 + 怎么验证"，验证手段统一用 Launch 会话、AppAnalyzer 和 HiTrace。

启动优化是整本书里"投入产出比"最高的主题之一：官方文档里的实测数据反复显示，把一段同步耗时挪出生命周期回调就能把启动耗时砍掉一个数量级（2.2 秒降到 220 毫秒的案例就在 19.2 里）。代价是你必须真的去读 Launch 泳道，而不是凭感觉改代码。
