# 第 24 章：应用可观测性

## 本章导读

前面所有章节讲的都是"开发态"：本地复现、本地抓取、本地分析。但真实世界的性能问题大多发生在用户设备上——你没有那台设备，没有那条网络，也没有那个特定的操作序列。应用发布后，质量保障只能靠数据：崩溃有没有涨、AppFreeze 发生在哪个页面、启动耗时分布是不是劣化了。

鸿蒙的线上质量体系由三层构成：

**端侧事件采集**：hiAppEvent 是系统级事件通道，应用可以订阅崩溃（APP_CRASH）、应用冻屏（APP_FREEZE）、冻屏告警（appFreezeWarning）、启动耗时、资源泄漏等系统事件，事件里带着系统服务填充的结构化字段——崩溃栈、主线程未处理消息、同步 binder 调用、全量线程栈、内存信息，比应用自己能抓到的信息丰富得多。

**性能打点**：HiTraceMeter 不止用于本地 Trace，关键路径上的 startTrace/finishTrace 同样是线上耗时数据的来源。配合启动耗时事件（系统打点，含点击时间与动效结束时间），启动质量可以完全不靠自埋点。

**平台侧聚合**：AppGallery Connect 的应用质量管理（APMS）提供崩溃聚类、启动和卡顿分析、冻结帧异常率等报表，是上架应用的现成质量看板；自建数据体系则通过 hiAppEvent 订阅 + 上报通道实现。

本章一节把这三层串成一条线：订阅什么事件、事件里有什么字段、打点打在哪、质量门禁怎么设。读完你应该能给自己的应用搭出一套"发布后第一天就能看到质量数据"的最小体系。

## 一个立场

可观测性体系最常见的失败方式不是没建，而是建了没人看。所以 24.1 在设计上有意保持克制：只订阅有明确处置动作的事件，只设会真的阻断发布的门禁。订阅十个事件但报警全部忽略，不如订阅三个事件且每条报警都有人跟进。线上数据的另一半责任是归因——报警响了之后要能回到本书第三部分的工具链里把根因挖出来，24.1 的末尾会把这条回路接上。
