# 第 21 章：内存实践

## 本章导读

第 4 章讲过方舟运行时的内存模型与 GC，第 10 章讲过内存问题的分类。这一章回答最实际的问题：应用内存涨了、被系统杀了、Snapshot 抓下来了——然后呢？

鸿蒙应用的内存问题有一个和 Android 不同的背景：ArkTS 对象的回收依赖方舟 GC，应用开发者没有手动 free 的机会，泄漏几乎全部来自"对象还被引用着，但业务上已经没用了"。引用从哪来？订阅没取消、单例持有了 context、事件总线挂着回调、全局缓存只进不出。这些模式的共同点是：**泄漏的对象在堆快照里看起来完全正常**，只有对比两张快照、数对象个数的增量，才能让它现形。

所以这一节的主线是 DevEco Profiler 的 Snapshot 对比工作流：怎么抓、怎么比、怎么从"新增数最多的类"一路追到代码里的那行订阅。围绕这条主线再讲三件事：内存水位与 GC 的观测（怎么知道内存"健康不健康"），图片/PixelMap 这一最大单项内存的治理，以及线上环境的泄漏获取手段（jsLeakWatcher、OOM 事件订阅）。

内存优化的验收标准不是"内存变小"，而是三个可量化结论：同一操作反复执行 N 次后内存是否回到基线；Snapshot 对比中目标类的存活数是否稳定；长时间运行后 PSS 是否无趋势性上涨。记住这三条，后面每一步操作都知道在验证什么。

## 与相关章节的分工

第 4 章回答"GC 什么时候会回收"——那是机制；第 10 章回答"内存问题分几类、各自走什么排查路径"——那是方法论；本章回答"拿到一台复现了内存增长的设备，接下来两小时做什么"——这是操作手册。三部分不重复：本章引用第 4 章的 GC 结论和第 10 章的分类，但所有步骤都以 DevEco Profiler 的具体操作为单位组织。如果你只想快速定位一个已知的泄漏，可以直接从 21.1 的"Snapshot 快照对比：标准工作流"一节开始，做完五步再回头补机制。

内存问题复现成本高，排查前先固定环境：同一台设备、同一个应用版本、关闭后台无关应用，操作序列用脚本或手写步骤固定下来。两张快照之间任何变量不一致（操作次数不同、中间弹过权限框），对比结果就没法看。另外强制 GC 是快照对比的前置动作——不触发回收就抓快照，增量里混着待回收对象，结论会偏。
